# RF-DETR / YOLO 集成必要性评估（承接 `local-detection-feasibility.md`）

> 起因：用户问「找图类功能有没有必要集成 RF-DETR 与 YOLO？有没有必要直接用别人训练好的模型/数据集做优化？」
>
> 本文是 [`local-detection-feasibility.md`](local-detection-feasibility.md) 的**续篇**，不重复其内容。
> 那份文档已论证 YOLO（§3/§11），但**成文时 RF-DETR 尚不存在**（Roboflow 2025-11 发布，ICLR 2026），
> 且「OpenCV 5 原生支持 RF-DETR」是**最近几天**才有的事。本文只补这两块新变量。
>
> ⚠ **本文数字分两类，请勿混用**：标「本机实测」的来自 §1.1 / §1.3（OpenCV 4.10）；
> 标「第三方」的来自 opendetect 基准（**ONNX Runtime + 未知硬件**）—— 后者**不可直接采信为本机结论**，
> 见 §4.2 的理由。

---

## 0. 一句话结论

| 问题 | 答案 |
|---|---|
| **找图类功能**要不要集成 RF-DETR / YOLO？ | **不要。** 找图与检测器解的是**两个不同问题**，不是「旧版 vs 升级版」的关系（§1）。 |
| 那检测器（不分型号）值得做吗？ | **值得，但落点只有一个**：替代 **VLM 识图**（10 800 ms → 45~85 ms）。且**排在「运动状态层」之后**（§7）。 |
| **RF-DETR 与 YOLO 选谁**？ | **许可证上 RF-DETR 完胜**（Apache-2.0 vs Ultralytics 全家 AGPL）；**但按本项目现状它跑不了** —— OpenCV 4.10 不支持 DETR 类模型，要么升 OpenCV 5，要么引 ONNX Runtime（§5）。 |
| 用**别人训练好的模型**？ | **不能直接用。** COCO 80 类里没有游戏元素/软件 UI（§6.1）。只能当**微调起点**。 |
| 用**别人的数据集**？ | **大概率无用**（目标域是用户私有的游戏/软件界面，公开数据集不可能覆盖）。真正的杠杆是 **RF-DETR 的小数据微调能力**（§6.2/§6.3）。 |

## 1. 先把三件事分开（这是本次评估最重要的一条）

用户问的「找图类功能」，在代码里对应 `FindTemplateOnScreenMulti`。**但 RF-DETR/YOLO 不是它的升级版。**

| 能力 | 回答的问题 | 本项目现状 | 正确工具 | 需要训练？ |
|---|---|---|---|---|
| **找图（模板匹配）** | 「**这个特定的**按钮/卡牌在哪」 | `image_match.cpp`：NCC 粗定位 → 邻域精修 → **逐像素终审**；毫秒~数十 ms | ✅ **模板匹配已是最优** | ❌ 不需要（截一张图） |
| **检测（类别）** | 「**任意一个**敌人/关闭按钮在哪」 | **VLM 识图 10 800 ms**（贵） | 检测器 / OCR / UIA | ✅ **需要** |
| **跟踪（运动）** | 「它**下一步**去哪」 | 曾落地后按正确性撤销 | `TrackerVit` + 运动模型 | ❌ 不需要 |

**★ 三者的关系不是替代，是分工：**

- 模板匹配有**像素级终审** ⇒ 对「找特定个体」这件事，它的精度**高于**任何检测器。
  检测器给的是「这个框里大概是那个类」，**没有像素级保证**。
- 检测器唯一的、模板匹配**做不到**的事是**类别泛化**：
  ① 目标有缩放/旋转/形变/发光/半透明 ⇒ 模板必然失配；
  ② 目标是**动画帧**（同一物体几十种姿态）⇒ 模板要截几十张图，检测器一个类就够；
  ③ 目标是**类别而非个体**（「任意一个敌人」）。
- 而这三条**全都要训练数据** —— 这正是本项目一直没做它的原因。

⇒ **「用检测器优化找图」这个方向本身不成立。** 与 `local-detection-feasibility.md` §3 结论一致：
模板匹配毫秒级，YOLOX-s 本机实测 65~356 ms（**更慢**）。RF-DETR 改变不了这个结论（§4）。

## 2. RF-DETR 是什么，以及它相对既有评估的位置

| 维度 | RF-DETR | 既有文档覆盖情况 |
|---|---|---|
| 架构 | **DINOv2 骨干 + LW-DETR / Deformable DETR**（Transformer，非 CNN） | ❌ 未覆盖（文档 §11 只有 RT-DETR，百度那个，**两者不是一回事**） |
| 输出 | **无 NMS**（端到端，DETR 家族特性） | 文档 §11.2 提到「NMS-Free 只能靠 RT-DETR」⇒ **现在多了一个选项** |
| 精度 | RF-DETR-n **48.4 mAP**（COCO） | 文档 §11.2 说「各版本 mAP 差异不如降输入尺寸重要」——**RF-DETR 让这条要重新算** |
| 许可证 | **N/S/M/L = Apache-2.0** ✅ / XL/2XL = PML 1.0 ❌ | ❌ 未覆盖 |

⚠ **不要把它和 RT-DETR 混为一谈**：RT-DETR 是百度的（Apache-2.0，CNN 骨干 + DETR 头）；
RF-DETR 是 Roboflow 的（DINOv2 骨干）。许可证都宽松，但**运行时要求完全不同**（§5）。

## 3. 许可证：RF-DETR **反超**了 YOLO 全家

这是本次评估里唯一一条**明确站在 RF-DETR 一边**的结论。

| 模型 | 许可证 | 本项目（闭源商业分发） |
|---|---|---|
| **RF-DETR N/S/M/L** | **Apache-2.0** | ✅ **可用** |
| RF-DETR XL / 2XL | PML 1.0 | ❌ 不用（也用不上，126M 参数） |
| YOLOv5/v8/11/26（Ultralytics） | **AGPL-3.0** | ❌ |
| YOLOv6/v7/v9 | GPL-3.0 | ❌ |
| YOLOv10 / YOLO-World | AGPL / GPL | ❌ |
| YOLOX / DAMO-YOLO / NanoDet / PP-YOLOE / RT-DETR | Apache-2.0 | ✅ |

Roboflow 官方 FAQ 明确：RF-DETR 核心模型与代码是 **Apache-2.0，无 copyleft 义务、无需购买商业许可**
（与 YOLO11 的 AGPL「闭源商用需买企业许可」形成直接对照）。

⇒ **在「许可证」这一格上，RF-DETR 是目前唯一能同时满足「Apache-2.0 + 高精度 + 免 NMS」的选项。**
但这**不足以让它进本项目** —— 卡在 §5 的运行时约束上。

## 4. 性能：第三方数据反直觉，但**不能直接采信**

### 4.1 第三方基准（opendetect，**ONNX Runtime，硬件未标明**）

| 模型 | 参数 (M) | FLOPs (G) | COCO mAP | **CPU 推理** |
|---|---|---|---|---|
| YOLOX-tiny | 5.06 | 16.4 | 32.8 | **≈18 ms** (57 FPS) |
| **RF-DETR-n** | 26.9 | 31.8 | **48.4** | **≈45 ms** (22 FPS) |
| YOLOX-s | 8.99 | 26.7 | 40.5 | ≈55 ms (18 FPS) |
| **RF-DETR-s** | 28.5 | 59.6 | **53.0** | ≈83 ms (12 FPS) |
| RF-DETR-m | 30.1 | 78.5 | 54.7 | ≈118 ms (8.5 FPS) |
| RF-DETR-l | 30.4 | 125.2 | 56.5 | ≈203 ms (4.9 FPS) |

**反直觉的一条**：`RF-DETR-n` 在 CPU 上（≈45 ms / 48.4 mAP）**比 `YOLOX-s` 更快且精度高 8 个点**。
「Transformer 在 CPU 上不划算」这个直觉在 DINOv2 + 小输入分辨率（RF-DETR-n 用 384×384）下**不成立**。

⚠ 但 RF-DETR 的**参数量是 YOLOX-tiny 的 5.3 倍**（26.9M vs 5.06M）⇒ 模型文件、内存占用、
首次加载时间都要按这个量级重估。

### 4.2 为什么这些数字**不能**直接写进本项目结论

| 理由 | 说明 |
|---|---|
| **运行时不同** | 上表是 **ONNX Runtime**；本项目是 **OpenCV dnn**。两者对 Transformer 算子的优化差距很大 |
| **硬件未标明** | 不知道那台 CPU 是什么。本机是 i7-13 代 16 线程 —— 需本机复测 |
| **RF-DETR 预处理更贵** | 官方基准注：RF-DETR 用 **576×576 + ImageNet 归一化**，YOLOX 用 letterbox ⇒ RF-DETR 的 `preprocess_ms` 明显更大 |
| **COCO mAP 不是本项目的口径** | 本项目只关心**自训练类**的召回/精度（`local-detection-feasibility.md` §3 已确立） |

⇒ **结论：所有第三方数字只能当「值得实测」的信号，不能当结论。** 实测路径见 §7 P0。

## 5. ★ 决定性约束：OpenCV 4.10 **跑不了** RF-DETR

这是本次评估里最硬的一条，也是**唯一真正卡住 RF-DETR 的地方**。

### 5.1 事实

- OpenCV 官方 DNN 文档中，**RF-DETR / YOLO26 的推理示例全部基于 OpenCV 5.0.0**，
  且明确提供「上一版教程（OpenCV 4 DNN）」链接作为对照 ⇒ **RF-DETR 支持是 OpenCV 5 的新能力**。
- OpenCV 5 对 DNN 引擎做了**重写**，核心改进正是 **动态形状（dynamic shapes）** 与 **子图（subgraphs）** 支持 ——
  这两项恰好是 DETR 类模型（变长 query、Deformable Attention）最需要的。
- OpenCV 5 的内置 DNN 引擎**目前仅 CPU** —— 对本项目**正好**（本来就只有 CPU 可用）。
- 另一种走法是 **ONNX Runtime**：OpenCV 5 把它做成了**可选集成**（需编译时启用），
  或直接引入 `onnxruntime.dll`。

### 5.2 本项目的现状与代价

```
build/Release/opencv_world4100.dll     61.7 MB   ← OpenCV 4.10.0（已随产品分发）
CMakeLists.txt:908/965  "/DELAYLOAD:opencv_world4100.dll"   ← DLL 名硬编码
```

| 路线 | 代价 | 风险 |
|---|---|---|
| **升 OpenCV 4.10 → 5.x** | major 版本升级：DLL 名变更（`/DELAYLOAD` 两处）、Caffe/Darknet 解析器移除、API 变更；模板匹配 / tracking / dnn 三块重度使用区都要回归 | **高**（牵动全项目，与「找图」无关的模块也受影响） |
| **引 ONNX Runtime** | +15~20 MB DLL，打破「零新依赖」前提（`local-detection-feasibility.md` §2 的核心卖点） | 中 |
| **不引 RF-DETR，用 YOLOX** | **零新依赖**（OpenCV 4.10 的 dnn 就能跑 CNN 类 ONNX） | 低 ✅ |

### 5.3 ⚠ 诚实标注

**「OpenCV 4.10 跑不了 RF-DETR」是依据官方文档的推断，本文未在本机实测。**
判据与实测方法见 §7 P0 —— **动任何代码之前必须先跑这一步**。

理由：官方只在 OpenCV 5 上演示；DETR 类模型需要的动态形状/子图支持是 5 的新特性；
但「具体在 4.10 上会以什么形式失败（`readNetFromONNX` 报 unsupported layer，还是 forward 时崩）」
未经实测。按本项目纪律，**未验证项必须显式标注**。

## 6. 「用别人训练好的模型/数据集做优化」——三种理解，三个不同答案

用户这句话包含三种可能，**必须分开回答**，否则会得出错误结论。

### 6.1 用别人的**预训练权重**（COCO）⇒ ❌ **不能直接用**

- COCO 80 类 = person / car / dog / chair … **没有任何一类是「游戏里的僵尸」或「某软件的保存按钮」**。
- 拿 `rfdetr-n.onnx` 直接跑本项目的场景 ⇒ **零可用输出**。
- 唯一正当用途：**当微调的起点**（backbone 特征复用），不是当成品。

⚠ 注意 `local-detection-feasibility.md` §11.1 已确立的同款陷阱：
**用了别人的预训练权重做起点，别人的许可证就跟着你的产物走**。
RF-DETR 这点是安全的（Apache-2.0），Ultralytics 的不安全（AGPL）。

### 6.2 用别人的**公开数据集**（Roboflow Universe 50 万+）⇒ ⚠ **大概率无用，但值得搜一次**

- 本项目的检测需求是「**用户自己的**游戏/软件里的元素」—— **高度私有**。
  公开数据集不可能覆盖某个具体游戏的角色皮肤、某个国产软件的图标。
- **唯一的例外**：如果落点是「**通用 UI 元素**」（按钮、图标、输入框、复选框），
  那确实存在可复用的公开数据集。但这时要注意 §6.4 —— **有更便宜的路径**。
- 值得做的动作：**在 Roboflow Universe 上按「game ui / icon / button / desktop automation」搜一次**，
  花 10 分钟确认有没有高匹配度的数据集。有则省标注，无则死心。

### 6.3 ★ 真正的杠杆：**RF-DETR 的小数据集微调能力**

这条才是「用别人的东西」这句话里**唯一有实质价值**的部分 —— 只不过「别人的东西」是
**别人的预训练方法**，不是数据。

Roboflow 官方主张（**注意：均为定性声明，官方未给量化数据**）：

- RF-DETR 的 **DINOv2 预训练骨干**擅长迁移到**新领域**；
- 「更强的预训练 ⇒ 从小数据中学习的能力更强，这对**没有 COCO 规模数据集**的任务非常重要」；
- 在小规模自定义数据集上，**收敛所需 epoch 数通常少于 YOLO**；
- 其发布的 **RF100-VL 基准**（100 个真实领域小数据集，专测**跨域迁移能力**）中，
  RF-DETR 是「唯一在所有类别中都排第一或第二的模型」。

⇒ **对本项目的意义**：如果真要做「用户自己标几十张图 → 训一个检测器」这条产品线，
**RF-DETR 比 YOLOX 更契合**（少样本泛化正是它的设计目标）。
这是 RF-DETR 相对既有文档里所有候选者的**实质优势**，也是它值得被单独评估的原因。

⚠ 但这条优势**救不了 §5 的运行时问题**：微调出来的还是 DETR 模型，
推理时依然要 OpenCV 5 或 ONNX Runtime。

### 6.4 别忘了：这三条替代路径**零训练、已落地**

即使「纯图标、无文字、无控件树」的场景真的出现，本项目**已有三条更便宜的路**：

| 路径 | 成本 | 状态 |
|---|---|---|
| **OCR 文字索引** | 已落地（`src/ocr_winrt.cpp`） | ✅ |
| **UIA 控件树**（桌面） | 系统 API，零训练 | ✅ |
| **周期网格推断**（卡槽/草坪） | 纯几何，零训练 | ✅ |
| 检测器 | **要标注 + 要训练 + 要 OpenCV 5** | ❌ 至今无真实案例 |

⇒ **维持 `local-detection-feasibility.md` §3.1 的结论：等真遇到那个场景再说。**

### 6.5 被忽略的门槛：**谁去标注、谁去训练？**

这是产品层面的根本矛盾，必须说清：

| | VLM 识图（现状） | 检测器方案 |
|---|---|---|
| 用户准备工作 | **零** | 标注 20~50 张图 + 跑训练（需 Python + PyTorch + GPU 或 Roboflow 云） |
| 单次耗时 | 10 800 ms | 45~85 ms |
| 适用性 | 任意界面 | **仅限训练过的类** |

⇒ 检测器把「每次 10.8 秒」换成「**一次性标注+训练 + 每次 45ms**」。
对**高频重复**场景（一局游戏点几百次）这是划算的；
对**一次性**场景（偶尔用一次的软件）这是**净亏损**。
**这不是技术问题，是产品定位问题** —— 决策前先明确目标用户是哪一类。

## 7. 建议

### P0（半天，**动任何代码之前必做**）：把新变量纳入基准，用本机数字替代第三方数字

复用**已存在**的 `tools/local_detection_bench/`（`local-detection-feasibility.md` §9 有完整复现方式）：

1. **决定性实验**：把 RF-DETR-n 导出 ONNX（opset 17，固定输入，`rfdetr[onnx]`），
   用 **OpenCV 4.10** 的 `readNetFromONNX` 加载并 forward。
   - **通过** ⇒ §5 的约束解除，RF-DETR 成为可行候选，进 P2；
   - **失败** ⇒ 记录**失败形式**（哪一层、什么错误），写回本文 §5.3。
2. **对照**：同机实测 `YOLOX-tiny` / `YOLOX-s` / `RF-DETR-n` 三者在 **OpenCV dnn** 与
   **ONNX Runtime** 下的耗时（含 `preprocess_ms`，RF-DETR 用 384×384，YOLOX 按原设定）。
3. 验收：`bench.exe` 能复现全部数字，并明确标注「OpenCV dnn」或「ONNX Runtime」。

### P1：**不做检测器**，先做「运动状态层」

`local-detection-feasibility.md` §11.5 ① 已论证：**几十行纯逻辑、可自检、不需要训练数据**，
且能顺带吸收 `TrackerVit` 那个 **84~110px 定位噪声**（现在拿单帧位置差分当速度 ⇒ 噪声直接变「跳变」）。
**性价比远高于任何检测器。**

### P2（仅在 P0 通过、且出现真实案例时）：`ILocalDetector` 抽象

- 接口 + ONNX 后端 + 输出解码 + NMS + 模型管理 ≈ 400~600 行（§4 Tier 1 评估不变）；
- ⚠ RF-DETR 的**解码与 YOLO 不同**（官方文档明确）：
  输出是 **raw** `dets`（归一化 cxcywh）+ `labels`（未激活 logits）；
  **必须按名称匹配输出**（`num_classes+1 == 4` 时与框的最后一维同形，按形状匹配会**静默对调**产生垃圾结果）；
  需自行 **sigmoid**（RF-DETR 用逐类 sigmoid，**不是 softmax**）；背景槽位随 checkpoint 布局变化。
- 接入点：**只替代 VLM 识图**，**不替代模板匹配**（§1）。

### P3：OpenCV 5 升级评估

**必须是独立决策，不能为了 RF-DETR 而升。** OpenCV 5 是 major 版本，会牵动
模板匹配 / tracking / dnn 三块重度使用区与分发链路（DLL 名、`/DELAYLOAD`）。
先评估 OpenCV 5 对**现有功能**的收益与风险，再谈它顺带解锁了 RF-DETR。

## 8. 明确不建议做的

| 不做 | 原因 |
|---|---|
| 用 RF-DETR / YOLO **替代找图（模板匹配）** | 模板匹配毫秒级 + **像素级终审**；检测器 45~356 ms 且对「找特定个体」精度更低（§1） |
| **直接**用 COCO 预训练权重 | COCO 80 类里没有本项目的目标类，输出全是垃圾（§6.1） |
| 为了 RF-DETR **立刻升 OpenCV 5** | major 升级牵动全项目，收益（解锁一个还没真实案例的功能）远小于风险（§5.2/§7 P3） |
| 引 Ultralytics 全家（v5/v8/11/26） | AGPL-3.0，闭源商业分发直接违规（§3） |
| 把模型打进默认安装包 | 违背既有约定（大组件走设置里下载） |
| 先做检测器、后做跟踪/运动层 | **顺序错了**：跟踪与运动层**不需要训练数据**，检测器需要（§7 P1/P2） |

## 9. 与既有文档的差异汇总（读旧文档时请注意）

| 既有文档的结论 | 本文的更新 |
|---|---|
