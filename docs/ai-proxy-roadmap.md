## 1. 多会话并行

### 1.1 你要的是什么（我的理解）

在 AI 助手里同时开多个对话标签（你截图里那个「桌面图标识别 ×」就是一个标签），
**每个标签独立跑**：一个模型开多会话、或多个模型各开一个，互不等待。

### 1.2 现在的硬阻塞（都已核实到代码）

| # | 阻塞 | 位置 | 后果 |
|---|---|---|---|
| ① | 桥等回执用**全局唯一** `waitingId_` | `ext_bridge_server.cpp` | 两条并发请求会**互相吞掉对方的回执**（表现成"莫名超时"） |
| ② | 驱动层一把**全局串行锁** `CallMu()` | `web_ai_driver.cpp` | 所有网页 AI 调用被强制排队 |
| ③ | **每站点只有一个**专属标签页 | 扩展 `qstWebAiOwnTab` | 两个会话写同一个输入框 ⇒ 串台 |
| ④ | 会话状态按 **provider** 分，不是按会话分 | `web_ai_backend.cpp` 的 `g_sessions` | 同站点的两个对话会共享"已发到第几条"⇒ 第二轮开始内容错乱 |
| ⑤ | 网页是**有状态**的：一个标签页 = 一条对话 | 站点本身 | 真并行必须**每个会话一个标签页** |

⚠ ③④⑤ 是**根本性的**：网页 AI 不像 HTTP API 那样无状态，
**"一个对话"就是浏览器里的一条标签页**。所以并行的物理形态就是"多个标签页"。

### 1.3 落地方案（按依赖顺序）

1. **桥：`waitingId_` → 按请求 id 关联**
   每个请求带唯一 id，回执按 id 唤醒对应等待者（`std::map<id, promise>`）。
   ⚠ 这是**唯一的真改动**，其余都是配套。改完必须补一条**并发回执不串台**的自检。
2. **驱动：去掉全局 `CallMu`**，改成**按标签页**串行（同一个 tab 上的操作仍须串行）。
3. **扩展：标签页从"每站点一个"改成"每会话一个"**
   `qstWebAiOwnTab` 的值从 `{provider: tabId}` 变成 `{conversationKey: tabId}`，
   `conversationKey` 由宿主生成（如 `provider#会话id`）。
4. **后端：`g_sessions` 的键从 provider 改成 conversationKey**。
5. **UI：**标签之间互不阻塞（现在是同一窗口的多个 tab，前端要把"正在跑"变成 per-tab 状态）。

### 1.4 风险与工作量

- **风险**：并发开多个标签页会**抢前台**（读回答需要页面可见，见 §15.2 的前台化）——
  两个会话同时前台化会互相打架。⇒ 真并行时得**串行化"前台化"这段临界区**（其它部分仍可并行）。
  ⚠ 这一条是设计里最容易被忽略、又一定会踩的。
- **工作量**：中等偏大（桥的并发模型 + 扩展的标签页管理 + UI 状态）。
- **建议**：**先做 1、2、4**（让同一标签页内的多会话排队但**不互相破坏**），
  再决定要不要 3（真并行）。

## 2. 提示词瘦身（首轮就发 30~50 KB 工具定义）

### 2.1 现状（已核实）

`web_ai_prompt.cpp` 的 `RenderToolList()` 会把**全部**工具（实测 36~48 个）
连同参数 schema 渲染进首轮提示词。实测占比：
- 有图轮次：工具定义占 **26.2%**
- 无图轮次：**32.2%**（`LESSONS.md` §25 的拆账）

而且它是**每轮重发**的（网页 AI 没有原生 tools 通道，只能当文本发）。
一轮 5~10 次工具调用 = 把那 30~50 KB 发 5~10 遍。

### 2.2 你的建议（我的理解）

"AI 需要调用、执行的时候再发 skill" ⇒ **按需加载工具定义**，而不是一上来全给。

### 2.3 成熟范式（**已核实有多个开源实现**）

这个做法叫 **Progressive Disclosure（渐进式披露）** / **Tool Search**：

- Anthropic 的 **Agent Skills** 就是这套：`SKILL.md` 只给 `name` + `description`，
  正文（详细步骤）**只在需要时才读进上下文**。
- 有实测数据：某 **226 工具**的 Agent 用 Tool Search 把上下文负载**降了 95.8%**
  （<https://arapaholabs.com/blog/2026-06-02-tool-search-progressive-disclosure>）。
  ⚠ **别把这个数套到我们身上**：那是 226 个工具的规模，而且它的 schema 比我们厚得多。
- 现成实现：`madnukem/lazy-skill-loader`（渐进披露式 skill 加载）。

⚠⚠ **我们实际能省多少（已实现并量过，见 `tool_catalog_is_far_smaller`）**：
`PlanTurn` 的**工具清单只在首轮发**（不是每轮重发）⇒ 这是**一次性**成本。
目录省掉的是「参数类型 + 必填标记 + 工具描述 160→48 字节」，
实测这个形状约 **2.2~2.5 倍**（不是数量级）。
**省不到更多的原因**：参数**名字**必须留着（模型要靠它拼 `arguments`），
短枚举也**刻意**留着（`button:left|right` 才 10 来字符，却能挡住"模型自己编个值"）。

### 2.4 落地设计（我们自己的提示词层，不碰扩展/桥）

**两阶段**：

```
首轮：只给「工具目录」——一行一个：名字 + 参数名 + 一句话（不含类型/长描述）
      + 一个元工具：loadTools(names: string[]) → 返回这些工具的完整定义

模型需要某个工具时：先输出 loadTools(["mouseClick","findImage"])
      程序把完整定义作为「工具结果」发回去（复用现有的 tool-result 通道）
      模型再输出真正的调用块
```

**关键设计点**：
1. **目录里的"一句话用途"必须够准** —— 它是模型选工具的唯一依据。
   写虚了（"执行点击操作"）模型就选错；要写**判据**（"点击屏幕上某个坐标"）。
2. `loadTools` 的返回**只发被要的那几个**，且**只发一次**（之后进会话历史）。
3. **兜底**：模型直接输出未加载工具的调用块时，**照样执行**（并记一笔）——
   不能让"忘了先 load"变成功能不可用。
4. **可测**：`WebAiSelfTest` 里加「目录不含 schema」「loadTools 只回被要的」「直接调用仍可执行」三条。

### 2.5 风险

- **多一轮往返**：模型要先 load 再调用 ⇒ 首轮多一次往返（约 5~15s）。
  但换来的是**后续每一轮**都省 30~50 KB ⇒ 净赚。
- **模型可能不用 `loadTools`**（我们的通道没有原生 function calling，靠约定协议）。
  ⇒ 必须有 §2.4 第 3 条的兜底，否则就是静默功能缺失。

**建议：这是三项里性价比最高的，优先做。**

## 3. 窗口反代（拖准星到目标窗口）

### 3.1 ⚠ 先纠正一个用词：「反代」在这里有两个完全不同的意思

| 做法 | 原理 | 例子 | 适用 |
|---|---|---|---|
| **A. 流量反代** | 拦截客户端与服务器的 **HTTP 流量**，转成 OpenAI API | `CLIProxyAPI`、`AIClient-2-API` | **只对走 HTTP 的 CLI 工具有效**（Codex CLI / Gemini CLI / Claude Code） |
| **B. 界面反代**（你要的） | 拖准星选中窗口 → **读窗口里的对话文本** + 往输入框打字 | 无成熟开源项目 | 任何 GUI 客户端 |

⚠ **已核实**：那三个热门开源项目（`router-for-me/CLIProxyAPI`、`justlovemaki/AIClient-2-API`、
`lbjlaq/Antigravity-Manager`）全是 **A 类**——它们拦的是 CLI 工具的 HTTP 请求。
**它们对纯 GUI 客户端（豆包客户端、Cursor 窗口）完全无效**，因为 GUI 客户端不发可拦的本地 HTTP。

⚠ 而且那篇文章自己就写明：这类做法**违反服务条款、会导致账号封禁**。
⇒ **我们不做 A 类**（与 `MEMORY.md` §14 的产品边界一致）。

**所以你要的 B 类，得靠我们自己的 UI 自动化能力做** —— 而这恰好是本项目的强项。

### 3.2 我们已有的零件（都在仓库里）

| 能力 | 现成实现 |
|---|---|
| 拖准星选窗口 | `src/desktop_tools/`（选区/准星叠层） |
| 读窗口里的**控件树 + 文本** | `src/window_mode/ui_element_probe.h`（UIA） |
| 读不到时的**视觉兜底** | OCR（`src/ocr_winrt.cpp` / Python OCR）+ 截图 |
| 往窗口**后台输入** | 后台窗口模式 + 假焦点注入（32/64 位 DLL） |
| 判定"回答是否生成完" | 我们已有的"内容稳定 N 毫秒"判据（网页端在用） |

⇒ **不是从零做，是把已有的零件按 `web_ai_driver` 的形态重新组一条链**。

### 3.3 分档可行性（**关键结论**）

| 客户端类型 | 例子 | 可行度 | 说明 |
|---|---|---|---|
| **Electron 系** | Cursor（VS Code 分支）、Claude Desktop、多数国产客户端 | **中高** | 理论上有 CDP，但需要客户端**带调试端口启动**（我们控制不了）⇒ 实际仍走 UIA |
| **原生 / Qt / 自绘** | 部分国产客户端、游戏式自绘 UI | **中** | UIA 树质量参差；自绘控件只能靠 OCR |
| **终端 TUI** | Codex CLI 之类 | **低** | 无稳定文本节点，只能截屏 + OCR 逐行解析 |
| **多标签/多会话** | 同上 | **更低** | 切会话要额外操作 |

### 3.4 建议方案（三步走，别一次铺开）

1. **先做豆包客户端一个**（你点名要的），验证链路：
   准星选窗口 → UIA 读对话 → 假焦点写输入框 → Enter → 等稳定 → 回读。
   ⇒ 产出一份 `window_ai_providers.json`（形态照抄 `web_ai_providers.json`）。
2. **抽象出"客户端适配配置"**：和网页端共用一套 schema（输入框判据、回答容器判据、忙闲判据），
   只是判据从 **CSS selector** 换成 **UIA 属性/自动化 Id**。
3. **再扩到第二个客户端**，验证这套抽象是否真的通用（**这一步才是真正的可行性验证**）。

### 3.5 风险（如实列出）

- **无稳定 selector**：客户端改版 ⇒ 适配失效（比网页端更频繁、更难远程修）。
- **流式渲染**：很多客户端逐字渲染，UIA 树每帧都在变 ⇒ 必须靠"内容稳定"判据（我们有）。
- **后台输入**：客户端常是 Electron，`PostMessage` 不向子窗转发（`LESSONS.md` §17）⇒
  大概率要走**假焦点注入**那条路，而它对某些客户端会被反作弊拦。
- **合规**：驱动用户自己的客户端 = 借用他自己已登录的会话，边界与网页端一致；
  **但绝不能做成"绕过客户端额度限制"**（那是 A 类，明确不做）。

**建议：先花 1~2 天做豆包客户端那一条链。成了再谈第二个。**

## 4. 本轮落地：窗口反代第一条链（2026-09-26/27，**真机跑通**）

> 对应 §3「界面反代」。**已实现并在豆包客户端上真机验证**；下面是拍下来的事实与坑。

### 4.1 交付物

| 文件 | 职责 |
|---|---|
| `src/web_ai/window_ai_profile.{h,cpp}` | **纯逻辑**：客户端档案合并、窗口匹配、输入框打分/挑选、相对矩形、答复提取、稳定判据、占位符判据 |
| `src/web_ai/window_ai_driver.{h,cpp}` | **驱动**：找窗 → 前台化 → UIA 抓取 → 定位输入框 → 写入（三档通道+回读）→ 提交 → 等稳定 → 读回（UIA/OCR 择优） |
| `AppDir()\window_ai_providers.json` | 客户端适配档案（用户覆盖层；内置豆包客户端 / Cursor / 终端 TUI） |
| `POST /qst/window-ai/probe` | 真机探针：候选窗口（含 `tooSmall` 标记）+ UIA dump + 输入框候选打分 + OCR 行框 + 干跑写入 + 可选真发 |
| `WindowAiSelfTest` | 18 例纯逻辑自检（进逻辑档） |

**与网页端共用**：`PlanTurn`（提示词规划）/ `ParseReply`（工具协议）/ OpenAI 响应构造 —— 只换了"传输层"。

### 4.2 真机证据（豆包客户端，D:\Doubao\Doubao.exe）

```
ok = True | mode = geometry-ocr | writeProof = verified | writeChannel = clipboard-paste
总耗时 17.0s（前台化 136ms / 焦点 456ms / 写入 1189ms / 提交 235ms / 等回答 13.5s）
replySource = uia-echo / ocr-echo（见 4.4）
```
屏幕上独立确认：`请只回答一个数字：3 + 4等于几？` 发出后，聊天区出现 **`7`** ✓；
`9+8` → **`17`** ✓；`11+12` → **`23`** ✓。

### 4.3 ★★ 三个决定性事实（都不是猜的）

| # | 事实 | 证据 |
|---|---|---|
| 1 | **Chromium 系客户端的 UIA 是「惰性开启」的**：第一次查询只回窗口框架（豆包 14 个 Pane+标题栏按钮、Cursor 0 个节点），再查才长出完整树（豆包 → **178 个节点**） | 连续两次探针 |
| 2 | 但**豆包客户端的 178 个节点里没有一个能当输入框**：唯一带 `ValuePattern+TextPattern` 的是整页 `RootWebArea`（面积≈整个客户区，打分 97 排第一），底部输入区**一个 UIA 节点都没有** | 全树枚举 + 按几何位置过滤 |
| 3 | 因此对这类客户端，**"定位输入框 + 读会话正文"两条都必须走几何 + OCR**；UIA 那份文本混着侧栏（914 字整页文本），OCR 那份会把消息操作**图标读成 `0`** | 实测：按长度择优 ⇒ 回答变成 `0` |

### 4.4 由此定下的几条判据（都已进自检）

| 判据 | 为什么 |
|---|---|
| `input.rectHint` + `reply.ocrRegion`（相对客户区 0..1）× 几何+OCR 路径 | 事实 2 ⇒ 没有 UIA 可定位 |
| **拒绝整页容器**：`automationId == RootWebArea` 或面积 ≥ 客户区 60% 一律不合格 | 否则会对整页 `SetValue`（事实 2 的 97 分候选） |
| **窗口尺寸下限**（默认 320x220）+ 面积最大者优先 | 豆包/Cursor 都有同进程的 **158x26 离屏小窗**同名，按"首个匹配"选就会对它打字（回执还"成功"） |
| **永不 Ctrl+A 清空**；输入框非空就**中止** | 在"编辑器+聊天面板"共存的客户端里 Ctrl+A 会选中**整个代码文件** |
| 空框会显示**占位符**（豆包：「发消息或按住空格说话．．」）⇒ 必须配 `placeholderHints` 且判严（开头 6 字内 + 总长 ≤40） | 否则把空框误判成"用户草稿"，**永远拒绝工作** |
| 答复定位必须**忽略空白**匹配提问回显 | OCR 会插空格：`11+12` 读成 `1 1 + 1 2` ⇒ 精确 `rfind` 必落空 ⇒ 整段会话被当回答 |
| 读会话**按"有没有提问回显"择优**（UIA / OCR） | 见事实 3 |
| 稳定判据 = **配置的空闲时长** + 至少两次读数 | 固定 1.2s 会把半截流式回答当最终答案 |

### 4.5 进度（2026-09-27 更新）

| # | 事项 | 状态 |
|---|---|---|
| 1 | **自动恢复被隐藏的客户端窗口** | ✅ **已实现**（详见 §4.6 的两个窗口陷阱） |
| 2 | **剪贴板优先读回答**（用户路线） | 🟡 通道 + 校准工具已就绪；**落点尚未校准准**（见 §4.6） |

| 5 | 终端 TUI（codex 之类） | ⬜ 未做（档案为"尽力而为"档，未真机验证） |

**#1 的实现要点**：候选池 = `ListSwitchableWindows` ∪ `EnumWindows`（含隐藏）；
严格标题匹配落空时**放宽到「进程名+尺寸」**（`titleExcludes` 仍尊重）；
`ShowWindow(SW_SHOW/SW_RESTORE)` 恢复；**并按"UIA 节点数 ≥ 8"逐个候选验活**；
`IsWindowOnCurrentVirtualDesktop()==0` 时用 `VirtualDesktopAccessor` **搬回当前桌面**。
回执里 `restoredFromHidden` / `movedToCurrentDesktop` 如实标出（不假装"本来就在那儿"）。

**#2 的实现要点**：UIA 名字/id 找「复制」→ 找不到用 `reply.copyButtonHint` 几何 → 点它
→ 轮询剪贴板变化 → **再读一次确认稳定**（防"生成中复制的半截回答"）→ 内容当回答
→ **把用户原来的剪贴板还回去**。两条纯逻辑判据（都进了自检）：
`PickWindowAiCopyButton`（**取最靠下的那个** —— 用户自己那条消息下面也有复制按钮，
点错就把提问复制回来）、`WindowAiClipboardReplyUsable`（变了/非空/不是提问/不离谱）。

### 4.6 ★★ 两个窗口陷阱 + 剪贴板通道的实测阻塞（**不是代码问题，是窗口状态**）

2026-09-27 12:26 探针实测（`POST /qst/window-ai/probe` 的 `clipboard` 段）：

```
target = Doubao.exe「」(restoredFromHidden=False, movedToCurrentDesktop=False)
controlCount = 6
```

#### 4.6.3 本轮同时修掉的一个**真阻塞**：输入框里我们自己留下的残字

实测：写进去但没提交成功时，输入框会**留着我们上一轮的 prompt**，于是后续每一轮都被
`INPUT_NOT_EMPTY` 挡回来（**整条链彻底不可用**，而回执看着很合理）。

修法（已生效，真发验证 `ok=True / writeProof=verified / 20.5s`）：
- 我们发出去的 prompt **记下来并落盘**（`AppDir()\window_ai_sent_prompts.json`，最近 8 条）——
  ⚠ 内存记忆一重启就没了，而残留会跨重启存在（第一版就栽在这）；
- 输入框内容若与某条记忆 **最长公共子串 ≥8 字且覆盖较短者 ≥60%** ⇒ 认定是我们自己的残留，
  **退格清掉**再写。
  ⚠ 为什么用 LCS 而不是 `find`/片段比对：**OCR 会认错字** ——
  「**请**只回答一个数字」被读成「**清**只回答一个数字」，一个字之差就让精确比对全部落空（实测）。
- 用户自己的草稿（与任何记忆、任何会话文本都不同源）**一律不动** —— 安全边界不变。


三次实测落点都没打中复制图标（`copyProbe.diag` 每次都回报锚点与落点）：

```
锚点=[1265,774,1368,801] 落点=(1255,829)   ← 锚到了**用户自己那条消息**（回答在它上面）
锚点=[1521,654,1625,681] 落点=(1511,709)   ← 同上，偏移也没对上
```

已实现但仍需一次校准的两处：
1. **锚点必须锁定"助手那条回答"**：现在的规则是"最靠下、且**不是我们刚发的提问**的文本"，
   而该排除只在**知道 prompt** 时才生效 —— 真发流程里传了 prompt，但回答在豆包客户端里
   常被渲染成卡片（`Group`）而非纯文本，锚点仍可能落到别处。
2. **偏移量**（默认 `dx=-0.014, dy=+0.034`，即文本左下角再往左 25px、往下 40px）
   要按客户端实测标定一次。

**校准步骤（10 分钟，不需要写代码）**：
① 真发一问 → ② 读 `window_mode_debug.log` 里那行「复制按钮（几何锚点）」
→ ③ 对着截图量出复制图标的真实坐标 → ④ 改 `window_ai_providers.json` 的
`reply.copyButtonOffset`（或直接给 `reply.copyButtonHint` 一个固定相对矩形）。
工具已经齐了：`copyProbe` 会把它算出的锚点与落点原样回报。

### 4.14 软悬停取操作栏 + 提问回声剔除（2026-09-28 夜）—— 部分完成
