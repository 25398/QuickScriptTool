# Real-time game automation: verified techniques for a fast, accurate screen->act loop
 Research for the Windows C++ RPA host (OpenCV locally, cloud VLM for grounding). Every claim carries a source URL. `UNVERIFIED` = not confirmable from a primary source; *(self-report)* = a project's own README number; *(2nd-hand)* = a community survey rather than the vendor. Punctuation note: ASCII only (`->`, `~`, `x`) so the file stays byte-safe across PowerShell round-trips.
## 0. Why the classic loop fails: the measured baseline

| System / source | Measured number |
|---|---|
| [OpenAdapt grounding](https://github.com/OpenAdaptAI/openadapt-grounding) | OmniParser full-image parse **724 ms**, +ScreenSeekeR crop **1418 ms**; UI-TARS **2724 ms** / **6914 ms** with crop (1922-element synthetic set) |
| [latent-bridge-games](https://github.com/19PINE-AI/latent-bridge-games) (arXiv 2606.24470) | reasoning VLM ~**1.5 s/decision**, "too slow for the ~15 Hz control loop"; slow-only ~**1 Hz / 4 s per decision**; fast+slow cold tick ~270 ms |
| [See, Symbolize, Act](https://ar5iv.labs.arxiv.org/html/2603.11601) (arXiv 2603.11601) | method section: "**The game is paused at every frame, and the VLM decides the next action**" |
| [Cradle](https://github.com/BAAI-Agents/Cradle) (arXiv 2403.03186) | RDR2 "requires real-time combat, so we need to **pause the game** to wait for GPT-4o's response and then unpause it" |
| [GamingAgent](https://github.com/lmgame-org/GamingAgent) | Tetris: "**Modify game speed to accommodate for AI gaming agent latency** ... change event time to 500~600 ms"; CLI has `--api_response_latency_estimate` |
| [UFO2](https://microsoft.github.io/UFO/ufo2/core_features/multi_action/) (arXiv 2504.14603) | speculative multi-action cuts LLM queries **up to 51%**, the best published round-trip reduction |

**Implication:** no published VLM-loop agent plays a real-time game without pausing or slowing it. To keep up with a moving scene the VLM must leave the per-action path. Everything below is ranked toward that.
## 1. Ranked techniques, by gain x ease (C++/OpenCV on Windows)

### 1.1 ROI-scoped capture (score 20): do this first
Never capture 1920x1080 and downscale; cost scales with area, so a 224x224 ROI is ~40x cheaper for both capture and matching.

| Fact | Detail |
|---|---|
| ROI size in practice | [AI-Aimbot-Assistant](https://github.com/HeXinjian-dev/AI-Aimbot-Assistant) captures **224x224** (radius 112 around the crosshair), reports ~4000 FPS for the capture thread and a **3-4 ms** capture->infer->post-process->move chain; its backend table is DXGI **<1 ms**, WGC **<2 ms**, GDI BitBlt **<5 ms** *(self-report)* |
| ROI must be stable | [Cradle RDR2](https://github.com/BAAI-Agents/Cradle/blob/main/docs/envs/rdr2.md) pins the game to 16:9 windowed-borderless at 1920x1080 / 2560x1440 / 3840x2160 ("DO NOT change the aspect ratio") and enlarges minimap icons; [GamingAgent](https://github.com/lmgame-org/GamingAgent) tells users to "capture only the gameplay window" and to crop the board exactly |
| DXGI release discipline | Microsoft: *"release the frame just before you call `AcquireNextFrame` ... minimize the time between the call to release the current frame and the call to acquire the next frame"* ([docs](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe)); canonical error handling (`DXGI_ERROR_ACCESS_LOST`, `DXGI_ERROR_DEVICE_REMOVED`, `DXGI_ERROR_SESSION_DISCONNECTED`, progressive-backoff retry) is in the [MS classic sample](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/DXGIDesktopDuplication/cpp/DesktopDuplication.cpp) |
| **Hybrid-GPU breakage (biggest risk)** | MS KB: *"the DDA does not support being run against the discrete GPU on a Microsoft Hybrid system. By design, the call fails together with error code `DXGI_ERROR_UNSUPPORTED`"* (0x887A0004); workaround is to run on the **integrated** GPU ([MS troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/error-when-dda-capable-app-is-against-gpu)). Ship a WGC/BitBlt fallback |
| WGC yellow border | Cannot be disabled from an unpackaged Win32 exe: `IsBorderRequired=false` needs `GraphicsCaptureAccess.RequestAccessAsync(Borderless)` + a `graphicsCaptureWithoutBorder` package capability + user consent; if denied the set "succeeds but the value will be ignored", and another app can set it back ([docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired)) |
| WGC `MinUpdateInterval` | Windows 11 build **22000+** (UniversalApiContract v13); the widely repeated "22H2" is `UNVERIFIED`; probe at runtime ([docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession?view=winrt-22000)) |
| WGC framerate bug | A community guide states WGC "only works correctly on Windows 11 24H2, due to a long-standing bug on other versions where it fails to capture at the target application's framerate"; same page: both APIs return black frames for DRM content, DXGI has Multi-Plane Overlay issues while WGC "recomposes MPO layers correctly" ([DXGI vs WGC](https://sageinfinity.github.io/docs/FAQ/dxgiwgc) *(2nd-hand)*) |
| Measured throughput | [DXcam](https://github.com/ra1nty/DXcam), 5900X + RTX 3090, 240 Hz output, 5 runs: **DXcam 239.19 FPS** (sd 1.25) vs python-mss **75.87** (sd 0.54) vs D3DShot **118.36** (sd 0.32); at a 60 fps target DXcam 61.71+-0.26, D3DShot 47.11+-1.33, mss N/A. README warns 1000+ FPS claims online are "busy-spinning a for loop on a staled frame" |
| GDI fallback | ~60 FPS and black screens in exclusive fullscreen; mss (~75 FPS) likewise fails there ([obs-snap-detector](https://github.com/chiguayeshao/obs-snap-detector/blob/main/RESEARCH.md) *(2nd-hand)*) |
### 1.2 Frame freshness: knowing you act on "now"

| Item | Detail |
|---|---|
| Clocks | WGC `Direct3D11CaptureFrame.SystemRelativeTime` = *"The QPC (QueryPerformanceCounter) time at which the compositor rendered the frame"* ([docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe.systemrelativetime)); DXGI gives `DXGI_OUTDUPL_FRAME_INFO.LastPresentTime` (QPC ticks) plus `AccumulatedFrames` (`>1` means you missed frames). `LastPresentTime == 0` means the desktop image was not updated, so guard against computing a huge age |
| Rule | `age_ms = (QPC_now - frame_ts) * 1000 / QPC_freq`; **abort the action if `age_ms` exceeds the time-to-next-frame budget**, the cheap correct "the scene moved" detector |
| Ready-made | dxcam `grab()` returns `None` when no new frame exists since the last call (`new_frame_only=False` forces latest); `get_latest_frame(with_timestamp=True)` returns `(frame, ts)` |
### 1.3 Hysteresis / temporal confirmation (score 20)
[OpenAdapt grounding](https://github.com/OpenAdaptAI/openadapt-grounding) measures the payoff: raw detections with 30% dropout give **~60-70% detection rate (min ~40%), "flickering"**; keeping elements stable in >50% of frames gives **80-100% and consistent** (`min_stability=0.5`), with resolution robustness holding from 800x600 to 1600x1200. Apply the same rule to a local detector: require *k* consecutive same-position matches before injecting input and *j* consecutive misses before releasing. [obs-snap-detector](https://github.com/chiguayeshao/obs-snap-detector/blob/main/RESEARCH.md) documents the tracker analogue ("ghost boxes" on empty scenes) fixed by `MAX_AGE=2..5` + Kalman velocity zeroing.
### 1.4 Normalized coordinates + crop-and-reground (score 15)
**(a) Ask for normalized coordinates.** Qwen2-VL set the convention: *"bounding box coordinates are normalized within [0, 1000)"* ([arXiv 2409.12191](https://arxiv.org/abs/2409.12191)). Integers avoid the model doing pixel arithmetic on a resized image and are resolution-agnostic; then snap locally by taking the returned point, cutting a +-5% crop and running `matchTemplate`/colour detection inside it. **(b) Crop and re-ask (test-time zoom-in).** [UI-Zoomer](https://github.com/ZJU-REAL/UI-Zoomer) (arXiv 2604.14113) is training-free and uncertainty-gated; measured ScreenSpot-Pro **+13.4** (Qwen2.5-VL-7B, 27.6 -> 41.0), +12.7 GUI-G^2-7B, +11.8/+8.6; UI-Vision **+10.3**; ScreenSpot-v2 **+4.2**. Gains concentrate on *icon* grounding and *spatial* categories, exactly the small-HUD case. The independent [OpenAdapt](https://github.com/OpenAdaptAI/openadapt-grounding) benchmark agrees: on harder/denser data OmniParser full-image drops to 90.1% while **+fixed cropping holds
98.2%**, and cropping lifts UI-TARS on <32 px elements from 28.6% to 50%. Cost is one extra VLM call: reserve it for the **first** grounding of a target, never per action.
### 1.5 Locate once, act many times (score 15)
The structural fix: ground once with the VLM, maintain every frame locally (S2), drive input from the local estimate, re-invoke the VLM only on tracker failure. Supporting mechanisms: **speculative multi-action** ([UFO2](https://microsoft.github.io/UFO/ufo2/core_features/multi_action/)) predicts a batch in one inference, validates each against live state, executes the valid ones and falls back to single-action on validation failure (**up to 51% fewer LLM queries**); UFO2's perception also fuses UIA metadata with OmniParser-v2 detections (YOLO-v8 + Florence-2 0.23B), deduped by IoU>10%, then Set-of-Mark ([paper](https://ar5iv.labs.arxiv.org/html/2504.14603v1)). **Streaming worker policies** ([GamingAgent](https://github.com/lmgame-org/GamingAgent)) run long-horizon and short-horizon workers concurrently, tuned by `--concurrency_interval` and `--api_response_latency_estimate`, so a late decision is still usable ("alternate" performed best in early experiments; *no accuracy numbers published*). **Action chunking** (ACT/ALOHA) is the robotics equivalent: predict a chunk, execute open-loop for k steps. `UNVERIFIED` for game agents, no measured result found.
### 1.6 Symbols, grids, Set-of-Mark (score 9): conditionally useful, can backfire
[Cradle](https://github.com/BAAI-Agents/Cradle) ships `icon_replacer.py` ("icons difficult for GPT-4 to recognize in the game can be replaced with text for better recognition"), `circle_detector.py` for RDR2 cooldown rings, a GroundingDINO minimap pipeline and a VideoSubFinder subtitler. [GamingAgent](https://github.com/lmgame-org/GamingAgent) has the user declare `--grid_rows/--grid_cols` plus a crop box, turning the Candy Crush board into a small labelled grid. [Set-of-Mark](https://ar5iv.labs.arxiv.org/html/2310.11441) is the general form: overlay region ids and let the model answer with an id, not coordinates (GPT-4V+SoM beat a fully finetuned referring-expression model on RefCOCOg zero-shot). **But the caveat is measured and severe:** [See, Symbolize, Act](https://ar5iv.labs.arxiv.org/html/2603.11601) gave models self-extracted object symbols alongside the frame and got *worse* results when extraction was unreliable: GPT-4o Space Invaders 130 -> **65**, Gemini-2.5-Pro 95 -> **80**, GPT-4o VizDoom 12 -> **8**. Detection F1: Claude-4-Sonnet **0.715**, Gemini-2.5-Pro **0.189**, GPT-4o **0.124**; symbol-only (no image) pipelines collapse. **Rule:** generate the marks *locally* so mark accuracy is yours, and let the VLM pick an id; never ask the VLM to both see and enumerate.
### 1.7 Verify-by-recapture, cursor parking, overlay exclusion (score 10)
Act only on a frame younger than one frame interval (S1.2); recapture immediately after the click and confirm the expected local change. [OpenAdapt](https://github.com/OpenAdaptAI/openadapt-grounding) states the same invariant for its product: "it halts instead of guessing ... using identity gates and independent effect verification." **Park the cursor** first: hover changes hover states/tooltips, and with WGC the cursor is baked in when `IsCursorCaptureEnabled` is true (dxcam: "If you need cursor rendering, use winrt", i.e. opt-in, so leave it off). **Exclude your own overlay:** desktop capture grabs the composited desktop, so boxes you draw are captured next frame and can be re-detected; fix by capturing a specific window (WGC) or masking the overlay rect ([obs-snap-detector](https://github.com/chiguayeshao/obs-snap-detector/blob/main/RESEARCH.md)).
### 1.8 Input pacing (score 9)
Fixed `Sleep()` pacing is not deterministic: a ~10-15 ms scheduler tick swamps a 16.7 ms frame budget. dxcam's older README credits the undocumented **`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`** with "+-1 ms" pacing vs `time.sleep` "(min resolution 16 ms)"; the current README says Python 3.11+ relies on improved `sleep()` and older versions "use WinAPI waitable timers directly" ([DXcam](https://github.com/ra1nty/DXcam)). [AI-Aimbot-Assistant](https://github.com/HeXinjian-dev/AI-Aimbot-Assistant) links `winmm.lib`, calls `timeBeginPeriod(1)`, and replaces sleep-based handshakes with a deterministic park/handshake protocol across capture, inference and input threads. Better than tightening the timer: make input **frame-driven**, i.e. capture -> detect -> act inside one iteration. [sunone_aimbot](https://github.com/SunOner/sunone_aimbot) adds the GPU-contention advice that matters here: cap the game's FPS, lower in-game resolution/graphics, "do not increase the object search window resolution", close browsers, because the capture/inference chain competes with the game for the same GPU.
### 1.9 OSS game-bot perception loops: what the mature bots actually do

| Project | Perception loop and documented tricks |
|---|---|
| [Sentdex/pygta5](https://github.com/Sentdex/pygta5) (2017 original, "legacy mode"; master is now a 2022 reboot) | Capture is **GDI BitBlt of the desktop** (`original_project/grabscreen.py`: `GetDesktopWindow` -> `GetWindowDC` -> `CreateCompatibleBitmap` -> `BitBlt(SRCCOPY)` -> `GetBitmapBits`; the lane keeper used `ImageGrab.grab(bbox=(0,40,800,640))`). ROI is a hard-coded polygon: `roi(img, vertices)` = `fillPoly` mask + `bitwise_and`, vertices `[[10,500],[10,300],[300,200],[500,200],[800,300],[800,500]]`; `process_img` = BGR2GRAY -> `Canny(200,300)` -> `GaussianBlur((5,5),0)` -> ROI -> `HoughLinesP`. **The crudest and most robust ROI trick of all:** *"this works when you have the game in **windowed mode, 800x600 resolution, at the top left of your screen**. You need this for both training and testing."* Robustness: `motion.py` stuck-detection = `absdiff` -> threshold **16** -> `countNonZero` compared to `motion_req = 800` over a **`deque(maxlen=25)`**, i.e. **25-frame confirmation** before firing a random escape. Pacing: `cv2.waitKey(25)` = **~40 FPS cap**, with the loop printing its own `'loop took {} seconds'`. Output: `directkeys.py` `SendInput` **scan codes** (`W=0x11 A=0x1E S=0x1F D=0x20`; press `0x0008`, release `0x0008|0x0002`). *Known bug not to copy: its `HoughLinesP(img, 1, pi/180, 180, 20, 15)` args are positional, so `20` lands in the `lines` slot.* The reboot drops screen capture entirely: an in-game mod feeds a **hood camera downscaled to 480x270**, 90 FPS split across 3 cameras = **30 FPS each**, with FPS and PPS as first-class console metrics |
| [ivan-guerra/colorbot](https://github.com/ivan-guerra/colorbot) (OSRS, Rust, Linux/X11) | Colour match is per-channel abs diff with **`const TOLERANCE: u8 = 3`** in plain RGB (**not HSV**); the click point comes from a **Graham-scan convex hull + ray-casting point-in-polygon** with `MAX_ATTEMPTS = 1000` and a **`MIN_EDGE_DISTANCE >= 10.0`** rule to avoid edge clicks. Template matching is `match_template_parallel` with **`SumOfSquaredErrors` (SSD, not NCC)** on grayscale, thresholded by an **area-scaled** bound `w*h*MAX_PIXEL_VARIANCE^2` with `MAX_PIXEL_VARIANCE = 15.0`. WindMouse for motion |
| [StaticSweep/ChromaScape](https://github.com/StaticSweep/ChromaScape) (OSRS, Java, Windows) | Region-scoped **HSV lower/upper ranges**; contour topology via `getChromaObjsInColour`; template matching with a **low-is-better threshold, "0.05 is often preferred, with the maximum being 0.15"** (SSD-style, not NCC); **OCR by template-matching glyphs, explicitly not ML** ("provides for OCR at runtime"), fonts pulled from [OSBC](https://github.com/kelltom/OS-Bot-COLOR) and [SRL](https://github.com/Villavu/SRL-Development). Robustness rules that generalise: **`clickMovingObjectByColourObjUntilRedClick` (click until the red interaction cross is detected)** = confirm-before-act; **state tracking by OCR of the XP counter with a timeout** (`Minimap.getXp` returning `-1` means stop); **occlusion rule "crop out the top 10 pixels"** for stacked items; **`waitRandomMillis(600,800)` described as "protect against lag or rendering delays"**; `waitRandomMillis(80,100)` between actions; a 1% chance of a 120-300 s break. Uses RemoteInput (below) |
| [Villavu/SRL-Development](https://github.com/Villavu/SRL-Development) (Simba/OSRS) | The richest *named* primitive set in this niche, and the best vocabulary to steal: **`Mainscreen.DidRedClick` / `DidYellowClick`** (confirm-before-act by observing click feedback), **`Mouse.Idle` / `Mouse.Miss` / `Mouse.Teleport`** (mouse parking and deliberate misses), **`Walker.DoMouseAhead`** (park the cursor along the path), `SRL.GetPixelShift` / `IsAnimating` (animation = scene moving), `Mainscreen.FindHPBars` / `FindHitsplats`, `XPBar.Read` / `Chat.GetChat` (HUD OCR), **`FindDTM`, `FindDTMRotated`, `FindDTMRotatedSE`, `FindBitmapToleranceIn`** (multi-scale/rotated template search), **`Walker.ScaleMinimap` / `ScaledSearch` / `FullSearch`** (scale-aware map search), `CTS0/CTS1/CTS2` colour-tolerance modes, `TPointArray.ConvexHull/MinAreaRect/MinAreaCircle/Cluster/Edges`, `Antiban.AddSleep/AddBreak/AddTask` |
| [kelltom/OS-Bot-COLOR](https://github.com/kelltom/OS-Bot-COLOR) (archived; upstream for ChromaScape) | *"We've modified OpenCV's template matching algorithm ... even supporting images with transparency"*, and the only latency figure in the OSRS set: **"OSBC can locate text on screen in as little as 2 milliseconds"** *(self-reported, hardware unstated)*. Python 3.10 only; Bezier mouse movement |
| [SerpentAI](https://github.com/SerpentAI/SerpentAI) (**archived**, default branch `dev`; README has a struck-through "End of life (November 2018)" then "Revival (May 2020)"; CHANGELOG stops at v2018.1.2) | Capture is `mss` in a **separate process** feeding **Redis** lists trimmed to `buffer_seconds*fps` = **150 frames**, and `FrameGrabber.get_frames()` **blocks until `llen > 149`, polling at 0.1 s**, i.e. a consumer cannot get a frame until ~5 s of footage accumulates. `GameFrameLimiter(fps=30)` (recording throttled to **10 FPS**). The focus gate is first-class: `if self.is_focused: on_game_frame(...) else: print("PAUSED"); time.sleep(1)`. Most copyable idea: **`GameFrame` exposes lazily-evaluated, cached variants**: half/quarter/**eighth-resolution**, eighth-resolution **grayscale**, full grayscale, and `ssim_frame` = **100x100 grayscale**, with `GameFrameBuffer(size=5)` and agent default `game_frame_buffer_size = 5`. Detection: `SpriteIdentifier` with `score_threshold=75` across three modes (top-8 signature colours, an **8-pixel constellation** exact-RGB check, SSIM) that **returns `"UNKNOWN"` below threshold, a built-in confirm-before-act**. `SpriteLocator.locate()` is an **anchor-pixel + verification** search: find one constellation colour, subtract its stored offset to get candidate anchors, verify all 8 points. OCR is `pytesseract` + skimage with Levenshtein fallback (`click_string` defaults `fuzziness=2`). Input: `SendInput` scan codes with extended keys via a `+1024` sentinel giving `0x0008|0x0001`, absolute mouse as `(x*65535)//display_width` with `0x0001|0x8000`, and a **20-step interpolation** (defaults 0.25 s move / 0.05 s tap); **`click_sprite`/`click_string` return `False` when the target is not found**. Limits: 30 FPS cap, requires focus, >=150-frame warm-up, archived |

**Transferable ideas worth stealing:** (1) **let the game draw the target for you**: RuneLite outline plugins reduce "find the NPC" to "find one RGB colour", the cheapest possible detector; the host equivalent is any in-game setting or addon giving a high-contrast marker (Cradle does this by enlarging RDR2 minimap blips). (2) **Pin the window geometry** so the ROI is a constant, not a per-session problem. (3) **Verify by the game's own feedback** (`DidRedClick`, the red interaction cross): cheaper and more reliable than re-detecting the target. (4) **Expose FPS/PPS as first-class metrics** in the loop (GamingAgent, pygta5-reboot); you cannot tune a latency budget you do not print. (5) **Precompute and cache frame variants** (SerpentAI's `GameFrame`): one downscale/grayscale per frame, reused by every detector.
### 1.10 Input realism (verified)

| Topic | Verified fact |
|---|---|
| **`SendInput` semantics** | Events are inserted **serially** and "are not interspersed with other keyboard or mouse input events inserted either by the user ... or by calls to `keybd_event`, `mouse_event`, or other calls to `SendInput`". It is **subject to UIPI**: "Applications are permitted to inject input only into applications that are at an equal or lesser integrity level", and when blocked it *"fails ... Note that neither `GetLastError` nor the return value will indicate the failure was caused by UIPI blocking"*, i.e. silent failure with a 0 return. It also "does not reset the keyboard's current state", so check `GetAsyncKeyState` first ([docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). `mouse_event` is documented as superseded ("Note: This function has been superseded. Use `SendInput` instead") |
| **Pointer ballistics: the correctness bug** | **Relative mouse motion IS ballistics-scaled.** [MOUSEINPUT docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput): *"Relative mouse motion is subject to the effects of the mouse speed and the two-mouse threshold values"*; above threshold 1 with speed != 0 the system **doubles** the distance, and above threshold 2 with speed = 2 it **doubles again**, so *"It is thus possible for the system to multiply specified relative mouse movement ... by up to four times."* [`mouse_event`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mouse_event) adds the second stage: speed 1-20, *"The default value is 10, which results in no additional modification"*. Full transform: `out = speed_scale(threshold_double(threshold_double(delta)))`. **So a 400 px synthetic flick can land as 400 / 800 / 1600 px depending on the user's Control Panel.** `MOUSEEVENTF_ABSOLUTE` has no threshold language (0-65535, maps to the **primary monitor** unless `MOUSEEVENTF_VIRTUALDESK` is set). Registry (`HKCU\Control Panel\Mouse`), community-verified not specified: `MouseSensitivity=10`, `MouseSpeed=1`, `MouseThreshold1=6`, `MouseThreshold2=10` plus `SmoothMouseXCurve`/`YCurve`. **Action: for deterministic relative aiming either force acceleration level 0 / sensitivity 10, or read `SPI_GETMOUSE` and invert the documented transform per machine**; the decoded default curve is not mild (segment gains ~2.5x -> 3.3x -> 4.9x -> **11x**). **Raw input bypasses ballistics entirely, verified verbatim:** [`RAWMOUSE`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawmouse): *"In contrast to legacy WM_MOUSEMOVE window messages Raw Input mouse events is not subject to the effects of the mouse speed set in the Control Panel's Mouse Properties sheet"*; Microsoft's [high-DPI mouse article](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/taking-advantage-of-high-dpi-mouse-movement): *"Windows applies pointer acceleration (also known as ballistics) to the raw mouse data"* for `WM_MOUSEMOVE`, while *"WM_INPUT has no ballistics applied to its data"*, and *"using DirectInput offers no advantages when reading data from mouse or keyboard devices, and the use of DirectInput in these scenarios is discouraged."* So: raw input / DirectInput = no ballistics; `WM_MOUSEMOVE` and `SendInput` relative = ballistics applied |
| `SetCursorPos` | *"The cursor is a shared resource"*; needs `WINSTA_WRITEATTRIBUTES`; *"The input desktop must be the current desktop"*; and it is **subject to `ClipCursor`**: *"the system automatically adjusts the coordinates so that the cursor stays within the rectangle."* Many games call `ClipCursor` while capturing the mouse, so a warp gets clamped. It also synthesizes no HID-level relative motion, so a Raw-Input game sees no delta. **Use `SendInput` relative moves as the primary path** |

### 1.11 Getting the capture loop right (the two mistakes that cost the most)
1. **Copy, then release immediately.** Microsoft's own performance rule: *"When the client acquires a frame, the client owns the surface; therefore the operating system can track only the updated regions and cannot copy desktop updates to the surface. Because of this behavior, we recommend that you minimize the time between the call to release the current frame and the call to acquire the next frame."* The correct pattern is **`AcquireNextFrame` -> `CopyResource`/`CopySubresourceRegion` into your own texture -> `ReleaseFrame` at once -> run detection on the private copy.** Holding the frame while you detect guarantees a coalesced (stale-looking) image *and* stalls OS updates ([ReleaseFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe)). OBS's DXGI path does exactly this (`AcquireNextFrame(0)` -> `CopyResource` -> immediate `ReleaseFrame`), and **OBS exposes no user-facing capture-buffer setting**: freshness is solved by not holding the frame, not by tuning a buffer.
2. **Read back only the ROI, and never block on `Map`.** `Map` *"gets a pointer to the data contained in a subresource, **and denies the GPU access to that subresource**"* and returns `DXGI_ERROR_WAS_STILL_DRAWING` if you pass `D3D11_MAP_FLAG_DO_NOT_WAIT` and the GPU is not finished. A full 1920x1080 RGBA readback is **8.294 MB**, so bandwidth is trivial and the cost is the **pipeline sync/stall**. Use GPU-side downscale, `CopySubresourceRegion` of just the ROI, dirty rects (`GetFrameDirtyRects`), and double/triple-buffered staging textures with `DO_NOT_WAIT` so the loop never blocks. **No reliable published ms figure for a 1080p readback was found; do not cite one, measure it.**

**GDI/mss throughput, for the fallback path** (**[measured](https://kylefu.me/2023/02/18/python-fast-screen-capture.html)** by Kyle Fu, 1920x1200 laptop, FPS mean+-sd): static Pillow 27+-0.5 / mss 29+-0.1 / DXcam **170+-3.4**; dynamic 22+-1.4 / 28+-0.7 / **96+-9.2**; small region 27+-0.7 / 57+-0.3 / **387+-11.4**; i.e. **a full-screen GDI grab is ~35-45 ms dynamic (about 22-28 FPS), 2-3 game frames of latency before you look at a pixel.** `mss` on Windows is **GDI `BitBlt` with `CAPTUREBLT` unconditionally** ([source](https://raw.githubusercontent.com/BoboTiG/python-mss/main/src/mss/windows/gdi.py)) and **cannot capture the cursor on Windows**. `CAPTUREBLT` is documented as *"Includes any windows that are layered on top of your window in the resulting image"* ([docs](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-bitblt)). Also copy mss's `SetProcessDpiAwareness(2)` call: **omitting DPI awareness breaks click coordinates on scaled displays.**

**End-to-end context:** the only rigorous public CUA latency study, **OSWorld-Human** ([arXiv 2506.16042](https://arxiv.org/abs/2506.16042)), reports agents *"taking tens of minutes for tasks humans complete in just a few"*, that *"large model calls for planning and reflection dominate latency, with later steps taking up to 3x longer than earlier ones"*, and that *"even top performers take 1.4-2.7x more steps than necessary."* For LLM agents the model call dominates; **for a game RPA tool that inverts, capture and input do.** No reliable published capture->detect->click breakdown was found.
### 1.12 Multi-frame patterns: the canonical "act once, repeat k times" evidence

| Source | Verified finding |
|---|---|
| Mnih et al. 2013, [arXiv:1312.5602](https://arxiv.org/abs/1312.5602), origin of frame skip | *"the agent sees and selects actions on every kth frame instead of every frame, and **its last action is repeated on skipped frames**. Since running the emulator forward for one step requires much less computation than having the agent select an action, this technique allows the agent to play roughly k times more games without significantly increasing the runtime. **We use k=4 for all games except Space Invaders** where we noticed that using k=4 makes the lasers invisible because of the period at which they blink. We used k=3..."*, and it *"applies this preprocessing to the last 4 frames of a history and stacks them"*, input **84x84x4** from **210x160 RGB at 60 Hz** |
| Machado et al. 2018, [arXiv:1709.06009](https://arxiv.org/abs/1709.06009) | *"Frame skipping restricts the agent's decision points by repeating a selected action for k consecutive frames"*; *"frame stacking ... reduces the degree of partial observability ... **making it possible for the agent to detect the direction of motion**"*; k=4 and k=5 are the common choices |
| OpenAI Baselines `MaxAndSkipEnv(skip=4)` | docstring *"Return only every `skip`-th frame"*; the **max-pool over the last two frames exists specifically to suppress Atari sprite flicker** |
| SB3 `AtariWrapper(frame_skip=4, action_repeat_probability=0.0)` | docstring: *"Frame skipping: 4 by default / Max-pooling: most recent two observations / Resize 84x84 / Grayscale / Clip reward / Sticky actions: disabled by default"*; code comment **`# frame_skip=1 is the same as no frame-skip (action repeat)`**. It has **no `frame_stack`** (separate `VecFrameStack`) and no range validation on `frame_skip` |
| TMRL ([trackmania-rl/tmrl](https://github.com/trackmania-rl/tmrl)), real-time TrackMania RL | runs at `time_step_duration: 0.05` = **20 Hz** with `IMG_HIST_LEN=4` (a 4-frame stack) at 64x64 grayscale. rtgym's docs: on **Windows 11 a 20 ms (50 Hz) target oscillates between 15 ms and 31 ms** because Windows `sleep` granularity is ~16 ms; on Linux 2 ms (500 Hz) is achievable. **The cleanest published measurement of why fixed sleeps fail** |

**Takeaways:** (a) committing to one decision for k frames is standard, and the failure that forced k=3 over k=4 (a blinking sprite becoming invisible) is exactly the risk, so gate k on the *effect* being observable rather than on a magic number; (b) stacking two frames is what makes *motion direction* observable at all, the cheapest answer to "is the scene moving"; (c) a max-pool over two frames is a documented, free de-flicker.

### 2.1 Recommended scheme, in order
1. **Sub-window NCC template match re-seeded from the last known box** (the "poor man's tracker"). Keep a patch from the moment the VLM grounded the target; each frame search only a small window around the previous position (32x32 template in a 128x128 search = 16x template area). `cv::matchTemplate(..., TM_CCOEFF_NORMED)` -> `cv::minMaxLoc` -> subpixel refine by fitting a parabola to the 3x3 neighbourhood of the peak. The peak is a thresholdable score. **Two caveats.** (a) **The masked path is serial**: `matchTemplateMask` branches out of `cv::matchTemplate` *before* the OpenCL/IPP/HAL paths, so masked matching gets **no SIMD or HAL acceleration**; masking a 1080p ROI every frame will not hold 30 FPS. Mask only if the template genuinely needs it, and keep the search window small. (b) Do **not** avoid masked `TM_CCOEFF_NORMED` out of fear of unsupported methods, it is supported; the risk is speed, not correctness. Masked `TM_CCOEFF_NORMED` costs about 4-5 cross-correlations.
2. **Global motion first, then local search.** `cv::phaseCorrelate` between consecutive downscaled frames gives camera pan; shift the predicted box by that delta, then run the NCC search. **Three traps, all source-verified.** (a) The returned `Point2d` is relative to the **image centre**, `center - t`, not corner-relative, so confirm the sign empirically before wiring it in. (b) `response` is *"the sum of the elements of r within the 5x5 centroid around the peak ... normalized to a maximum of 1"* and the source then divides by the **padded DFT** size, so thresholds are not intuitive. (c) `createHanningWindow` returns the **square root** of the Hann window and the window must be **exactly the image size** (`CV_Assert`), so cache one window per resolution. Docs: [motion analysis](https://docs.opencv.ac.cn/4.13.0/d7/df3/group__imgproc__motion.html).
3. **`cv::calcOpticalFlowPyrLK` on a small set of `goodFeaturesToTrack` corners** of the patch, taking the median displacement. Cheap at low feature counts and it fails *visibly* (few tracked points), which makes the re-anchor trigger trivial. **Cap `maxCorners` in the low hundreds**: a third-party benchmark measures `goodFeaturesToTrack` at ~**90 ms per call at 1920x1024 for 10,000 corners** (`qualityLevel=0.05, minDistance=5`, CPU unstated, order-of-magnitude only; [source](https://www.cnblogs.com/Imageshop/p/17802677.html)). The OpenCV `lk_track` sample recipe is a good start: `maxCorners=500, qualityLevel=0.3, minDistance=7, blockSize=7`, `winSize=(15,15)`, `maxLevel=2`, re-detect every 5th frame, and reject points failing the forward-backward check `abs(p0-p0r).max(-1) < 1`. For dense flow, `DISOpticalFlow` preset `DISOPTICAL_FLOW_PRESET_FAST` (patch_size 8, patch_stride 4, grad_descent_iter 16, variational_refinement_iter 5); the DIS paper claims "300Hz up to 600Hz on a single CPU core" but its own footnote says **1024x436 at 42-46 Hz including preprocessing**, which is the honest number ([arXiv 1603.03590](https://arxiv.org/abs/1603.03590)). `FarnebackOpticalFlow::create()` defaults are `numLevels=5` (not 3), `winSize=13`, `polyN=5`, `polySigma=1.1`.
4. **A learned tracker from the main module when scale/rotation matters.** Prefer **`TrackerVit`** (767 KB, `getTrackingScore()`), then `TrackerDaSiamRPN`, then `TrackerNano` (CPU-only). `TrackerGOTURN`'s own header warns it "does not handle occlusions" while being "fairly robust to viewpoint changes, lighting changes, and deformations"; occlusion is the common case for a HUD, so rank it last. A TensorRT NanoTrack deployment claims **up to 250 FPS** ([NanoTrack_Tensorrt_Cpp](https://github.com/ZhangLi1210/NanoTrack_Tensorrt_Cpp) *(self-report)*).
5. **Classical CSRT/KCF/MOSSE** only if OpenCV is rebuilt with contrib; S2.2 explains why that is a bad trade.
### 2.2 Why CSRT/KCF/MOSSE are not the answer, even if you build them
**Measured CSRT cost.** An OpenCV forum user profiled `TrackerCSRT` on a Jetson Nano under OpenCV 4.10.0: `tracker->init()` = **1,766,909 us (~1.77 s)**, `tracker->update()` = **764,138 us (~764 ms)**, versus 25-30 FPS on the same board with OpenCV 4.5.0; a companion thread reports **<1 FPS** and is titled "extremely slow" ([profile](https://forum.opencv.org/t/trackercsrt-is-extremely-slow-with-opencv-4-10-0/19072), [<1 fps](https://forum.opencv.org/t/how-do-i-get-real-time-performance-out-of-this-csrt-object-tracker/19199)). *Caveat: Jetson Nano ARM CPU, desktop x86 is far faster. The structural point holds: `init()` is about 2.3x `update()`, so never re-initialise a correlation-filter tracker per frame.*

**Confidence internals (read from the OpenCV/opencv_contrib sources):** `TrackerDaSiamRPN::update()` returns `true` **unconditionally regardless of score**, so its bool is useless and you must use `getTrackingScore()` ([source](https://raw.githubusercontent.com/opencv/opencv/4.x/modules/video/src/tracking/tracker_dasiamrpn.cpp)). `TrackerNano::getTrackingScore()` is the max of the score map ([source](https://raw.githubusercontent.com/opencv/opencv/4.x/modules/video/src/tracking/tracker_nano.cpp)). In contrib, MOSSE computes a real PSR `(maxVal-mean)/stddev` with `psrThreshold=5.7` and learning `rate=0.2` but **exports no accessor** ([source](https://raw.githubusercontent.com/opencv/opencv_contrib/4.x/modules/tracking/src/mosseTracker.cpp)); CSRT's `psr_threshold` (default 0.035) is compared against the **raw response max**, not a true PSR, despite the name ([source](https://raw.githubusercontent.com/opencv/opencv_contrib/4.x/modules/tracking/src/trackerCSRT.cpp)); KCF's `detect_thresh=0.5f` likewise. There is no `cv::TrackerMOSSEModel` in any OpenCV version, so **OpenCV exposes no usable PSR/confidence for MOSSE or KCF**.

**Default configurations and the game failure mode** (all read from the sources above):

| Tracker | Default config that bites | Consequence in a moving scene |
|---|---|---|
| MOSSE | `rate=0.2` (very aggressive model update); `randWarp` with `C=0.1`; `size` fixed by `getOptimalDFTSize` at init | **No scale handling at all** (FOV zoom / resolution change mis-boxes the target); the fast update lets the model absorb an occluder and stay corrupted |
| KCF | `resize=true, max_patch_size=80*80`, so **the whole frame is silently downsampled 2x** once the ROI exceeds 6400 px^2; `wrap_kernel=false`; `detect_thresh=0.5` on a raw, unnormalised max | Small HUD features are destroyed by the 2x downscale; a non-normalised threshold means behaviour changes from scene to scene |
| CSRT | `admm_iterations=4`, `template_size=200`, `number_of_scales=33`, `scale_step=1.020`, ~18 HOG + ~10 colour-name + gray channels; internal segmentation is a 16-bin **HSV** histogram with `check_mask_area` falling back to `default_mask` when the segmented mask is <5% of the object | Structurally the most expensive of the set; **breaks on low-saturation / white / semi-transparent HUD art and on heavy bloom**; the mask fallback degrades silently to an unsegmented filter. Escape hatch: `setInitialMask()` lets you supply your own segmentation prior |
| MIL | `samplerTrackInRadius=4`, `samplerSearchWinSize=25`, 250 Haar features | Small search radius, so a camera whip or fast pan leaves the search window entirely; no confidence output |
| GOTURN | 227x227 patch CNN, needs the caffemodel on disk | Header's own warning: **"does not handle occlusions"**, and occlusion is the normal case for a HUD |
| DaSiamRPN / Nano / Vit | `windowInfluence` window penalty biases toward the previous location; fixed `exemplarSize`/`instanceSize` (Nano 127/255, DaSiamRPN 127/271) | **Lag under fast motion**; a depleting health bar or shrinking orb is out-of-distribution for the appearance model |
### 2.3 Documented OpenCV caveats that decide the HUD-detection recipe
Verified from the OpenCV 4.12.0 docs (mirror `docs.opencv.ac.cn`, canonical `docs.opencv.org`; the canonical host 403s automated fetches) plus the 4.10.0 sources.

| API | Documented fact / failure mode |
|---|---|
| `matchTemplate`, **flat-template trap** | **The highest-value silent failure in this report.** The source contains `if (templNorm < DBL_EPSILON && method == CV_TM_CCOEFF_NORMED) { result = Scalar::all(1); return; }`, and the masked path has the same guard on `norm_templx`. A near-uniform template therefore scores a **perfect 1.0 at every position** (typically reported at pixel (0,0)). Guard by rejecting low-variance templates at capture. Related: `minMaxLoc` returns only *one* peak; OpenCV's own Python tutorial notes *"cv.minMaxLoc() won't give you all the locations"* and thresholds the result map instead (it uses `threshold = 0.8` with `TM_CCOEFF_NORMED` **on a Mario screenshot**, with no NMS, so expect duplicate clusters) |
| `matchTemplate`, cost model | CPU `matchTemplate` is **always DFT-based** (`crossCorr` -> `hal::DFT2D`, tiled, `blockScale=4.5`, `minBlockSize=256`). The only "naive for small templates" test (`dft_size = 18`) is **OpenCL-only**, and IPP bails out by **area** (`if (templ.area()*4 > img.area()) return false`). There is **no documented DFT threshold at all**, so the "naive below 18 px" note is folklore. Normalised paths use `integral(img, sum, sqsum, CV_64F)`; `TM_SQDIFF` on `CV_8U` is computed internally in `CV_64F`. **The masked path bypasses OpenCL, IPP and the HAL entirely.** Derived bound: a 32x32 template over a full 1080p image is ~2.06 G MAC naive, which is why ROI scoping is not optional |
| `phaseCorrelate` | `response` = *"the sum of the elements of r within the 5x5 centroid around the peak ... normalized to a maximum of 1"*; the source then divides by the padded DFT `M*N`. The returned `Point2d` is **image-centre-relative**. `createHanningWindow` returns **sqrt(Hann window)** and must match the image size exactly |
| `matchShapes` (Hu) | Docs define `m_i = sign(h_i)*log(h_i)` and `I1 = sum abs(1/m_i^A - 1/m_i^B)`, so any Hu moment at or near zero makes `log()` diverge and `1/m_i` blow up, which is the documented-math basis for the usual "unstable, not really rotation/scale robust" criticism. No accuracy percentage found: `UNVERIFIED` |
| `contourArea` | *"the area is computed using the Green formula. Thus, the returned area and the number of non-zero pixels ... can be different. Also, the function will most certainly give a wrong result for contours with self-intersections."* So run `approxPolyDP`/`convexHull` before trusting area on a noisy mask |
| `HoughCircles` | *"Usually, the function detects the centers of the circles well. However, **it may not find the correct radius**"*; fix with `minRadius`/`maxRadius`, or `maxRadius<0` to return centres only. `HOUGH_GRADIENT_ALT` wants `dp=1.5` and `param2~0.9` ("measure of circle perfectness", lower to 0.8-0.85 for small circles); its `param1` is the upper Canny threshold, Scharr-based, so use ~300. Documented spurious-circle fix: `GaussianBlur(7x7, sigma 1.5)`, or the sample's `Size(9,9), 2, 2`. For cooldown rings the cheaper alternative is `minEnclosingCircle` plus a circularity ratio `4*pi*A/P^2` from `contourArea` and `arcLength`, avoiding Hough entirely |
| `connectedComponentsWithStats` | 8- or 4-connectivity; `ltype` `CV_32S`/`CV_16U` only; **label 0 is always background**, so exclude it when counting HUD blobs; the parallel version engages *"if at least one of the parallel frameworks is enabled and the number of rows ... is at least twice the value returned by `getNumberOfCPUs()`"*. `CCL_SAUF` forces row-major label ordering |
| `goodFeaturesToTrack` | Defaults: `(img, corners, maxCorners, qualityLevel, minDistance, mask=noArray(), blockSize=3, useHarrisDetector=false, k=0.04)`; pipeline is min-eigen/Harris -> 3x3 non-max suppression -> sort -> drop within `minDistance`; `maxCorners<=0` means unlimited. ~90 ms at 1080p for 10k corners (third-party), so keep it in the low hundreds |
| Dense flow | `DISOpticalFlow` FAST preset = the constructor defaults (`finest_scale=2, patch_size=8, patch_stride=4, grad_descent_iter=16, variational_refinement_iter=5, coarsest_scale=10`); MEDIUM uses `finest_scale=1, stride 3, gd_iter 25, var_refine 5`. `FarnebackOpticalFlow::create()` defaults to `numLevels=5` (**not 3**); `calcOpticalFlowFarneback` itself has no defaults |

**Multi-scale template matching, the exact published recipe** ([PyImageSearch, 2015-01-26](https://pyimagesearch.com/2015/01/26/multi-scale-template-matching-using-python-opencv/)): `for scale in np.linspace(0.2, 1.0, 20)[::-1]`, i.e. **20 linearly spaced scales from 1.0 down to 0.2** (step
0.8/19 = 0.042105). The frame is resized with `imutils.resize(gray, width=int(gray.shape[1]*scale))`, which wraps `cv2.resize` with **`INTER_AREA`**; both template and frame are converted to `Canny(50, 200)` **edge maps**; the match method is **`cv2.TM_CCOEFF`** (note: *not* `TM_CCOEFF_NORMED`, so there is no usable absolute threshold); the best `(maxVal, maxLoc, scale)` is kept and the box rescaled. The article's own limits: *"we can handle variations in translation and scaling, our approach will not be robust to changes in rotation or non-affine transformations"* and *"template matching does not do a good job of telling us if an object does not appear in an image"*. **Cost: 20 `matchTemplate` + 20 `resize` + 20 `Canny` full-frame passes per frame**, viable only on a small cropped search window, never full 1080p.
### 2.4 Re-anchor policy
Run the local tracker every frame and treat its box as a *hypothesis*, not truth. Re-invoke the VLM grounder only when: the NCC peak stays below threshold for k consecutive frames; PSR collapses; the box hits the search-window edge (target leaving ROI); or the patch's mean colour histogram diverges past a threshold (scene changed / target occluded). On re-ground, **verify the new box against the old** (IoU gate + expected-size gate) before executing anything, because an unverified re-ground is how a bot clicks the wrong thing. HUD gauges (health bars, cooldown rings) are better handled by colour-threshold + contour geometry (`inRange` -> `findContours` -> `contourArea` / `minEnclosingCircle`, with morphological open/close and area + aspect-ratio filters) than by a general tracker; Cradle's `circle_detector.py` is the reference. `UNVERIFIED`: no published accuracy/latency numbers found for that recipe. Two OpenCV gotchas here: the 8-bit HSV **hue range is 0-179**, not 0-360, so a red health bar needs **two** `inRange` calls merged; and HUD art is often low-saturation, near-white or semi-transparent under bloom, which is exactly where naive HSV thresholds break.
## 3. Myths: commonly believed, does not work
1. **"Downscale the screenshot before sending it to the VLM to save tokens/latency."** Accuracy collapses with resolution. [See, Symbolize, Act](https://ar5iv.labs.arxiv.org/html/2603.11601): Claude-4-Sonnet object-detection F1 **0.31 at Atari's native 160x210** vs **0.68 at 1280x720** (~2x); per game 0.28 -> 0.58 (Pong), 0.31 -> 0.71 (Breakout), 0.35 -> 0.75 (Space Invaders); performance flattens only once the *shorter side* reaches ~720 px. **Crop, don't downscale.**
2. **"A better/bigger VLM will ground the game frame."** Same source, same frames: Claude-4-Sonnet F1 **0.715** vs Gemini-2.5-Pro **0.189** vs GPT-4o **0.124**. Prompting does not close that, and both weaker models *lost* score when handed their own extracted symbols.
3. **"Feed the VLM a video / more frames and it will keep up."** Every published game-agent result using per-frame VLM decisions **paused the game** ([See, Symbolize, Act](https://ar5iv.labs.arxiv.org/html/2603.11601);
   [Cradle](https://github.com/BAAI-Agents/Cradle)) or **slowed it down** ([GamingAgent](https://github.com/lmgame-org/GamingAgent): Tetris 500-600 ms per event). More frames cannot beat a 0.7-7 s round trip ([OpenAdapt](https://github.com/OpenAdaptAI/openadapt-grounding)). Frame *stacking* helps for a different reason: it makes motion direction observable (S1.12).
4. **"Just use `TrackerCSRT` / `TrackerKCF`."** (a) They are **not in this build**: OpenCV 4.10.0 here has no `opencv2/tracking.hpp`, so CSRT/KCF/MOSSE/MedianFlow/Boosting/TLD need `opencv_contrib` (S2.0). (b) Measured CSRT `init` ~1.77 s / `update` ~764 ms on a Jetson Nano; the thread is literally titled "extremely slow" and a companion thread reports "<1 fps". KCF is fast but has no scale model and silently 2x-downsamples large ROIs. Neither exposes a confidence; `TrackerVit`/`TrackerNano`/`TrackerDaSiamRPN` do.
5. **"`matchTemplate` masks only work with `TM_SQDIFF` and `TM_CCORR_NORMED`."** Historically true, now obsolete, **and OpenCV's own tutorial is the source of the stale claim.** The mask parameter dates to OpenCV 3.0.0; the two-method restriction held from 3.0.0-rc1 through 4.3.0 and was lifted in 4.4.0. Meanwhile the **current** 4.x C++ tutorial still prints *"Only two matching methods currently accept a mask: TM_SQDIFF and TM_CCORR_NORMED"* (`doc/tutorials/imgproc/histograms/template_matching/template_matching.markdown`), and the Python tutorial never mentions masks at all. For 4.10.0 all six work, including masked `TM_CCOEFF_NORMED`, but the masked path silently bypasses OpenCL and the HAL (CPU-only).
6. **"A 1.0 match score means the target is there."** No: a flat or near-uniform template **silently scores 1.0 everywhere**, usually reported at (0,0). Reject low-variance templates at capture time and treat a 1.0 at (0,0) as failure (S2.3).
7. **"`pyautogui.locateOnScreen` is slow because template matching is slow."** The cost is the *capture*: pyautogui's own docs give `screenshot()` at **~100 ms for 1920x1080** and locate calls at **1-2 s**, i.e. capture-dominated. `grayscale=True` buys ~30% *"but potentially causing false-positive matches"*; `confidence` requires OpenCV. Same conclusion as S1.11: fix capture and scope, not the matcher.
8. **"`SendInput` is indistinguishable from real input."** False and provably so: every injected event is flagged (`LLMHF_INJECTED` / `LLKHF_INJECTED`) and there is no supported way to clear it (S1.10).
9. **"`SendInput` is all you need."** `SendInput` relative moves are *ballistics-scaled*, so identical code produces 400 / 800 / 1600 px flicks on different machines; `SetCursorPos` is clamped by a game's `ClipCursor`; `PostMessage` never reaches input state; and UIPI silently returns 0 when the target runs at higher integrity. Only `uiAccess="true"` (Authenticode-signed, installed under `Program Files`) is documented to fix both UIPI and the foreground restriction, and Microsoft scopes it to accessibility apps.
10. **"`Sleep(16)` gives you 60 Hz pacing."** No: a request up to ~3 ms is quantised to the ~15.6 ms system tick, so *every* sleep-based scheme is a 64 Hz scheme (S1.10). Use `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (measured floor ~0.52 ms), or better, let `AcquireNextFrame` be your wake-up.
11. **"Symbolic / annotated overlays always help the VLM."** Only when the symbols are accurate; see the measured degradations in myth 2's source. Generate marks locally and let the model select an id.
12. **"`mss`/GDI BitBlt is fine for games."** No: mss on Windows *is* GDI `BitBlt` with `CAPTUREBLT` unconditionally, cannot capture the cursor, and measured 29 FPS static / 28 FPS dynamic at 1920x1200 where DXcam got 170 / 96 ([measured](https://kylefu.me/2023/02/18/python-fast-screen-capture.html)). Both mss and BitBlt reportedly black-screen in exclusive fullscreen, and DXGI itself fails outright on hybrid-GPU laptops.
13. **"Grab a full screenshot and pass a fresh frame each action."** Frame age is measurable (S1.2); the correct primitive is "act on a frame whose age is under one frame interval", not "act on whatever we last grabbed".
14. **"The OpenCV docs publish a tracker FPS/Coverage comparison table."** They do not. A full search of the
    4.12.0 and 4.5.5 Doxygen indexes finds no tracker comparison table and no "Coverage" token anywhere; the `group__tracking` page is two sentences, and the "Introduction to OpenCV Tracker" tutorial covers only create/`selectROI`/`init`/`update` and lists only MIL, BOOSTING, MEDIANFLOW, TLD, KCF, GOTURN, MOSSE (no CSRT, DaSiamRPN or Nano). The familiar MIL/Boosting/MOSSE FPS table comes from a **LearnOpenCV blog post**, not OpenCV, and is `UNVERIFIED` here (that page was unreachable). Do not cite it as documentation.
## 4. Verified vs. must-measure
**Verified from primary sources above:** all capture/input API semantics; the OpenCV 4.10.0 build contents and `matchTemplate`/`Tracker*` behaviour; every measured number quoted (DXcam 239/75.87/118.36 FPS; GDI 27-29 vs DXcam 96-170 FPS; CSRT init 1.77 s / update 764 ms; OpenAdapt 724-6914 ms; UI-Zoomer +13.4/+10.3/+4.2; See-Symbolize-Act F1 0.31 -> 0.68 and 0.715/0.189/0.124; UFO2 -51%; detection rate 60-70% -> 80-100%; `Sleep(500 us)` -> 15.5 ms vs high-res timer -> ~0.53 ms; timer tick 15.625 ms; pyautogui screenshot ~100 ms).
**Must measure on the target hardware, because no public number exists:**
- `matchTemplate` cost for your actual template/search sizes. The only published data points are a tiny case (64x64 haystack, 12x12 needle, `TM_CCOEFF_NORMED` -> **0.28 ms** on an i9-7920X, **0.14 ms** on an i7-9700K, SO 60097895) and `goodFeaturesToTrack` (~90 ms/1080p for 10k corners, third-party). **No published ms figure exists for a 1920x1080 `matchTemplate`; do not invent one.**
- GPU->CPU readback cost (1080p RGBA = 8.294 MB; the cost is the sync/stall, not bandwidth) and `phaseCorrelate` / LK / DIS / `HoughCircles` / `connectedComponentsWithStats` at your resolutions.
- Your own `age_ms` distribution and pacer overshoot.
- ORB/AKAZE + `findHomography` RANSAC for UI anchors: **essentially un-researched here.** No measured ms and no citable failure-mode source. The usually-quoted failure modes (self-similar textures -> ambiguous matches; flat UI -> too few keypoints; RANSAC needing >=4 non-degenerate inliers) are plausible but **uncited**. Entry points:
  [ORB](https://docs.opencv.org/4.x/db/d95/classcv_1_1ORB.html), [AKAZE](https://docs.opencv.org/4.x/d8/d30/classcv_1_1AKAZE.html), the "AKAZE and ORB planar tracking" tutorial (`doc/tutorials/features2d/akaze_tracking/`), Lowe IJCV 2004.
- **No accuracy or latency figure exists for HSV-`inRange` + `findContours` HUD detection.** It is per-game HUD art, and it is the de-facto default in this niche yet entirely unquantified. Treat any number as invented.
- WGC `MinUpdateInterval` exact minimum OS build (probe at runtime); EasyAntiCheat primary docs (unreachable).

**Corrections to widely-circulated claims**, worth knowing because they mislead: `matchTemplate`'s `mask` dates to OpenCV **3.0.0**, not 4.0; `IDXGIOutputDuplication::GetFrameStatistics` **does not exist** (`PresentCount` is on `IDXGIOutput::GetFrameStatistics`, full-screen only; `AccumulatedFrames` is on `DXGI_OUTDUPL_FRAME_INFO`); `Farama-Foundation/Gym-Retro` and `tmrlproj/tmrl` are **404** (correct: `Farama-Foundation/stable-retro`, `trackmania-rl/tmrl`); pygta5's master is no longer the 2017 project; the dxcam README has **no** `PIL.ImageGrab` column and no per-resolution rows.
