## 0. 一句话结论

| 问题 | 答案 |
|---|---|
| 有没有可行性？ | **有，而且是本项目"最后一块缺口"的正解** —— 但**不是**做成"内置 AI 助手"，而是做成**离线定位后端**（§2）。 |

| 建议怎么落地？ | 复用**既有 OCR 可选组件管线**（§8），本地模型作为**同级候选**接入 `FuseLocateCandidates`，**不是先验**（§6）。 |

## 1. 先把"本地 AI"这个词拆开

用户说的"本地 AI"有三种完全不同的东西，**选错一种整个方案就废了**：

| 理解 | 是什么 | 对本品有用吗 |
|---|---|---|
| ① 本地**聊天/文本 LLM**（如 Qwen3-0.6B 纯文本） | 能说话，**看不见屏幕** | ❌ **无用**。"看图点击"它做不了 |
| ② 本地**通用 VLM**（能看图能说话，如 Qwen2.5-VL-3B） | 看得见，但**为通用对话设计**，定位是副业 | ⚠ **能力够、CPU 跑不动**（§4.2） |
| ③ 本地**GUI 定位专家模型**（VLA / grounding） | 输入「截图 + 一句描述」→ 输出**一个坐标** | ✅ **这才是本品要的** |

⇒ **本方案只谈 ③。** 它是"看图点某个界面"这件事的最小充分模型：
**输出只有几个 token（坐标），不需要长文本生成，不需要对话，不需要规划。**

## 2. 边界：它到底替代谁？（这一节决定值不值得做）

本品**已经有四条感知路径**（这是既有事实，不是设想）：

| # | 路径 | 回答的问题 | 成本 | 状态 |
|---|---|---|---|---|
| 1 | **模板匹配**（`FindTemplateOnScreenMulti`） | "**这个特定的**按钮在哪" | 毫秒~数十 ms，**像素级终审** | ✅ 已落地，且**已是最优** |
| 2 | **OCR 文字索引**（WinRT 内置 / 可选 RapidOCR） | "写着『保存』的按钮在哪" | 几十 ms | ✅ 已落地 |
| 3 | **UIA 控件树**（桌面） | "名字叫 X 的控件在哪" | 系统 API，零成本 | ✅ 已落地 |
| 4 | **云端 VLM 识图** | "**用自然语言描述的**任意目标在哪" | **10 800 ms**，要 API key + 联网 | ✅ 已落地 |

**缺口只有一处**：**无文字、无控件树、且不是已存模板的目标**（游戏 HUD、canvas 界面、自绘控件），
且**用户没有联网 / 没有 API key / 不想付钱**。

⇒ 本地定位模型的**唯一正当落点**：**做第 5 条路径，专补这个缺口**。

**★ 它不替代任何一条既有路径**（重复既有结论，但必须再钉一次）：

| 想替代 | 结论 |
|---|---|
| 替代模板匹配 | ❌ **更慢且更差**（模板匹配毫秒级 + 像素终审） |
| 替代 OCR | ❌ OCR 读文字比它稳，且更便宜 |
| 替代 UIA | ❌ UIA 是精确矩形，它给的是"大概在这" |
| **替代云端 VLM 识图** | ✅ **唯一落点**：10.8 s → ~0.5 s，且离线 |

### 3.3 落地的精度预期（**必须打折看**）

ScreenSpot 是"给一句描述 + 截图 → 给一个点"，与本品场景同构，但：
- ScreenSpot 是**学术标注的干净截图**；本品面对的是**真实桌面（多显示器、缩放、DPI、动画）**；
- GoClick-B 的 74.1 是**它在自己数据上微调后**的成绩；**Florence-2 原版零样本做 grounding 会明显更低**（**未实测**）。

⇒ **诚实的预期**：
- **本地模型首次尝试命中率：60~75%**（推算 + 打折，**待实测**）；
- **加既有校验闸后的"可交付成功率"**：拒绝率上升，**错点率应压到 <2%**（靠 §7 的校验链，不是靠模型变准）。

⚠ **不要拿"74.1"当产品指标**。**未实测前，一切精度数字只能当方向。**

## 4. ★ 决定性的技术判断：只能选 encoder-decoder 的 0.2~0.8B

这是本文**最容易被做错**的一步。用户说"不要占用太多性能"，而**性能的真凶不是参数量，是视觉 token 数**。

### 4.1 两类架构的算力差在哪

| | encoder-decoder（Florence-2） | decoder-only VLM（Qwen2-VL / ShowUI） |
|---|---|---|
| 图像怎么进去 | **一次 ViT/DaViT 前向**（固定分辨率，如 768×768） | 切成**视觉 token** 塞进序列，**随分辨率平方增长** |
| 768×768 的视觉 token | 1 次编码（不占生成序列） | ≈ **729 ~ 1000+** |
| 1344×1344 的视觉 token | — | ≈ **2500+** |
| prefill 代价 | **~0.3 TFLOPs** | **~19 TFLOPs**（ViT ~12.4 + LLM ~6.9） |
| 生成 | 坐标约 **6 个 token** | 同样约 6 个 token（但 prefill 已付完） |

### 4.2 折算到本机算力基线（**推算，基于本仓实测**）

基线来自 `local-detection-feasibility.md` §1.1 **本机实测**：
`YOLOX-s`（26.7 GFLOPs）@640 在 **16 线程 = 257 ms** ⇒ **有效算力 ≈ 100 GFLOP/s**。

| 模型 | 估算 FLOPs | 本机（16 线程，int8）**推算** | 弱机（4 线程）**推算** |
|---|---|---|---|
| **Florence-2-base @768** | **~0.3 TFLOPs** | **~1~3 s** | ~4~12 s |
| Florence-2-large @768 | ~1 TFLOPs | ~3~10 s | ~12~40 s |
| **ShowUI-2B / Qwen2-VL-2B @1344** | **~19 TFLOPs** | **~60~190 s** ❌ | **~240~760 s** ❌ |
| Qwen2-VL-2B @512（大幅降分辨率） | ~2.8 TFLOPs | ~9~28 s ❌ | ~36~112 s ❌ |

**⚠ 本节初稿（2026-09-23 早）把 Florence-2-base 写成「~30~50 GFLOPs ⇒ ~0.5 s」，那是错的**
（漏算了 BART 编码器要把 **576 个图像 token** 整个编码一遍）。正确量级见上表，**修正说明见 §16**。

> ⚠ **上表全部是"推算"，不是实测**。算力基线 100 GFLOP/s 来自本机 16 线程（fp32 OpenCV dnn）；
> int8 + VNNI 的 ONNX Runtime 大约快 2~4 倍（上表按此取值）。但"折算是否线性"**未验证**
> （Transformer 的 attention 与 CNN 的算子效率不同，两个运行时也不同）。
> **实测方法与验收见 §12 P0 —— 不要引用本表的推算值对外承诺。**
> **结论方向不变**：encoder-decoder 比 decoder-only 便宜一个数量级以上。

### 4.3 ⇒ 结论（**这一条请照做**）

| 结论 | 说明 |
|---|---|
| **只考虑 0.2~0.8B 的 encoder-decoder** | Florence-2-base（首选）/ large（备选） |
| **2~3B 的 decoder-only VLM 在 CPU 上直接出局** | 不是"慢一点"，是**慢 100 倍以上**（推算），与"低延迟"直接冲突 |
| **不要因为 ShowUI/ZonUI 精度高 2~6 个点就选它们** | 精度差 2~6 点，速度差 **两个数量级** |
| **若将来引 GPU（ONNX Runtime + DirectML）** | 那时再重估 2~3B 选项（≈ +20 MB DLL，见 `local-detection-feasibility.md` §1.3） |

## 5. 运行时分发方案

| 项 | 选择 | 理由 |
|---|---|---|
| 推理运行时 | **ONNX Runtime**（CPU EP） | Florence-2 是 seq2seq（含 beam search / KV cache / 自定义解码），**OpenCV dnn 跑不了**；ORT 对 Transformer 算子优化成熟 |
| 体积代价 | **+15~20 MB**（`onnxruntime.dll`） | ⚠ **打破"零新依赖"**（`local-detection-feasibility.md` §2 的卖点仅对 CNN 类成立，该文档 §9 已自我修正过同类问题）⇒ **必须放进可选组件，不进默认包** |
| 模型格式 | ONNX（int8 优先，q4f16 备选） | int8 ≈ 236 MB，精度损失需实测；q4f16 ≈ 145 MB 更小 |
| ⚠ 模型路径编码 | **必须 GBK / CP_ACP** | **本仓已踩过**：`readNet*` 不认 UTF-8，**连纯英文目录也失败**（用户名含中文）⇒ 用 `WideToAcp()`，**不是** `ToUtf8()`。ORT 的 `Ort::Session` 收 `const wchar_t*`，但**自检里必须有一条真模型加载用例**当守门员（见 `local-detection-feasibility.md` §10.4） |
| 运行线程 | 跟随既有 `SyncImageMatchThreadBudget()` | ⚠ **低性能模式必须硬禁用本地推理**（既有前科，见 §7 红线 4） |
| 内存 | 权重 ~240 MB + 激活 ⇒ **峰值 400~600 MB**（推算） | 需在设置页明示；低性能模式禁用 |

## 6. ★ 接入点：本地模型是**同级候选**，不是**先验**

这是本方案与"已撤销的 Florence 集成"**最本质的区别**。

### 6.1 正确的接入位置

`src/ai_locate_verify.h` 已有现成的融合函数：

```cpp
/// 视觉候选 + UIA 锚点 → 聚类选点。
AiLocateFusionResult FuseLocateCandidates(
    const std::vector<AiVisionCandidate>& cands,   // ★ 本地模型的输出进这里
    const std::vector<AiUiAnchor>& anchors,
    double iouMatch = 0.5,
    const std::wstring& targetText = std::wstring());
```

**做法**：本地模型输出一个 `AiVisionCandidate`，**与云端 VLM 的候选放进同一个 `cands` 向量**，
然后**照走既有全套逻辑**（聚类选簇 → `JudgeLocateConfidence` 定级 → 遮挡校验 → 点击 → 点击后画面变化校验）。

**收益（这才是关键）**：
- **不引入新判据** —— 复用已经过大量日志打磨的门闩，风险面最小；
- **天然获得"双票一致"信号** —— 本地与云端**都指向同一处**时 `clusterSize ≥ 2`，
  置信度天然更高；**不一致时**（各说各话）系统本来就会保守处理；
- **可 A/B 对比** —— 两者都在同一坐标系、同一套判据下，精度可量化比较。

### 6.2 尝试顺序（降级链，与 `OcrBackendAttemptOrder()` 同款思路）

```
① 模板匹配（毫秒，像素终审）        ← 有模板就用它，永不变
② OCR 文字索引 / UIA 控件树          ← 有文字 / 有控件树就用它
③ ★ 本地定位模型（~0.5 s，离线）      ← 本轮新增：无①②可用时的第一选择
④ 云端 VLM 识图（10.8 s）            ← ③低置信 / 校验不过时**升级**到它
```

**顺序理由**：③ 比 ④ **快约 20 倍且免费**，所以 ③ 必须在 ④ 之前；
但 ③ 精度更低（§3.3），所以 ④ 保留为**升级路径**，不是删掉。

⚠ **设置里必须能选**：`auto`（默认，按上表）/ `localOnly`（纯离线，无网环境）/ `cloudOnly`（现状，零行为变化）。

## 7. ⚠⚠ 三条红线（来自 Florence 被撤销的真实前科，**不许重犯**）

`vision-agent-gap-audit.md` 明确记录了 Florence/local_grounding **被删除的原因**，逐条转成设计约束：

| # | 前科（原文） | 红线（本方案必须遵守） |
|---|---|---|
| 1 | 「Florence → CorrectLocate 先验 \| **毒化云端 → NOT_FOUND**」 | **绝不允许把本地模型的猜测当作先验喂给云端模型**。本地与云端必须是**独立候选**，各自从原始截图出发。**先验会污染强模型**——强模型会被弱模型的错误框带偏，且表现为"云端也找不到"，比本地单独失败更糟。 |
| 2 | 「Florence Zoom 直接点击 \| **粗框偏则裁掉真目标**」 | **绝不允许用本地模型的粗框直接裁图再做二次定位**（裁偏 = 真目标被裁掉，后续全废）。要用它的输出，只能在**整图**上按坐标点。 |
| 3 | 撤销声明：「引擎**只做感知 + 执行 + 如实回执**，绝不替模型做决定，**也绝不保留跨帧世界状态**」 | **本地模型是无状态的单次感知原语**：一次输入 → 一次输出 → 交回调用方。**不许**在引擎侧维护"目标还在老地方"这类会话状态（`ai_locate_track`/`ai_locate_cache`/`ai_ui_layout` 已因此全部撤销）。 |
| 4 | 「低性能模式必须硬禁用本地推理」（`local-detection-feasibility.md` §6.1，实测 1 线程时 YOLO 直接不可用） | **低性能模式开启 ⇒ 本地模型整体禁用，回落既有链路**，与 `SyncImageMatchThreadBudget()` 同款处理。 |
| 5 | 「OpenCV 符号守卫必须在任何 `cv::Mat` 出现之前」（同上 §6.2） | 同类问题在 ORT 上依然存在：**任何调用 ORT 的入口前面必须有 `LocalVisionAvailable()` 守卫**，且守卫要在**任何 ORT 对象构造之前**。漏了 = 抛异常把进程当场带走（没日志、没结束音）。 |

> **一句话**：本地模型的定位是**"一个更便宜、更弱、离线可用的候选来源"**，
> 不是"一个更聪明的引擎"。**它说话，引擎照旧校验；它不说话，一切照旧。**

## 9. 自研方向（用户明确问了）

### 9.1 ★ 本品有一个别人没有的资产：**免费的 GUI grounding 训练数据**

`src/ai_logic_convert.h` 的 `AiLogicTranscriptEntry` 已经是**训练样本的雏形**：

```cpp
struct AiLogicTranscriptEntry {
    ScriptAction action{};          // 动作
    std::wstring locateTarget;      // ★ 自然语言目标描述（= 训练用的 prompt）
    std::wstring templatePath;      // ★ 当时的模板图（= 样本图的一部分）
    int screenX = 0, screenY = 0;   // ★ 真实点击点（= ground truth 标签）
    bool fromLocate = false;        // ★ 是否来自定位（= 是否可当样本）
    double settleSec = 0.0;
};
```

**即 `(截图, 自然语言描述, 点击点)` 三元组 —— 正是 GUI grounding 的标准训练格式。**

再叠加两处**自动标注**能力：
- **正样本**：`ai_locate_verify.cpp` 的 `JudgeLocateConfidence` / 点击后画面变化校验**通过的**记录；
- **负样本**：**校验失败的**记录（`定位缓存作废：点击后画面无变化`、`遮挡校验失败`）⇒ **天然难例**，
  这正是 `local-detection-feasibility.md` §4 Tier 1 说的"跟踪失败的那些帧天然就是难例"的升级版。

**数据从哪来**：产品自己的用户在真实任务里跑，**日志自动积累**；且**云端 VLM 可离线批量重跑**，
把它的定位结果当**教师信号**（这就是**蒸馏**，不是人工标注）。

### 9.2 这个方向的可行性有论文背书

- **GoClick（2026-04）** 证明了：**Florence-2 架构 + 0.23B 参数 + 数据配方** ⇒ **ScreenSpot 74.1**，
  对标 7B 模型（§3.2）。它用的正是 **encoder-decoder + 高质量数据筛选**（3.8M 精选自 10.8M）。
- 它同时证明了**未微调的小模型做 grounding 很差**（原始 Qwen2-VL-2B = 17.9）⇒
  **"自研"的实质不是从头训，而是"把云端 VLM 的定位行为蒸馏进 0.23B"**。
- ⚠ **GoClick 权重未发布、许可未声明**（本文已核实）⇒ **不能直接用它的产物**，
  但它的**方法**（架构选择 + 数据配方）**可以照做**。

### 9.3 两个具体的工程优化（**均待实测**）

| 优化 | 做法 | 预估收益 | 风险 |
|---|---|---|---|
| **词汇裁剪** | Florence-2 的 BART 词表 51,264 token，而 grounding 输出只需 `<loc_0>..<loc_999>` + 数字 + 少量结构 token（**约 1,200**）。嵌入矩阵 = vocab × d_model(768) × 4B ⇒ **157.6 MB**（与实测 `embed_tokens` 完全吻合）。裁到 1,200 ⇒ **≈ 3.7 MB** | **省 ~39 MB(int8) / ~78 MB(fp16)** | ⚠ 裁剪后**只能做 grounding**，不能再做 caption/OCR（若还要通用能力，得留大词表） |
| **输入分辨率下调** | DaViT 编码器是耗时大头；768→512 可再省约一半 | 速度约 ×2 | ⚠ 小控件（<16px）召回会掉；**必须实测**（本品要点的常是小图标） |

### 9.4 自研的三条**不做**

| 不做 | 原因 |
|---|---|
| **从头训练**一个 GUI grounding 模型 | 需要百万级标注 + 多卡训练；**收益与"微调 Florence-2"相同** |
| 自己做**大规模数据标注** | 用产品日志 + 云端 VLM 蒸馏**成本低一个数量级**，且更贴本品场景 |
| 把模型做成**通用 VLM**（能聊天能看图） | 本品要的是**定位原语**；通用能力只会**换更大的模型**（回到 §4 的死路） |

## 10. 明确不建议做的

| 不做 | 原因 |
|---|---|
| 引 **2~3B decoder-only VLM**（ShowUI / ZonUI / Holo1.5） | CPU 上 **100 秒级**（推算 §4.2）；精度只高 2~6 点，速度差两个数量级 |
| 用本地模型**替代模板匹配 / OCR / UIA** | 三条都更便宜更准（§2） |
| 把本地模型的**粗框当先验**喂云端 | **已撤销的 Florence 就是这样死的**（§7 红线 1） |
| 用本地模型**直接裁图**再定位 | 裁偏则真目标被裁掉（§7 红线 2） |
| 用 **OmniParser 的 `icon_detect` 权重** | 基于 YOLOv8 ⇒ **AGPL-3.0**，闭源商业分发违规（§3.1） |
| 把模型 / ORT **打进默认安装包** | 违背既有约定（大组件走设置里下载）；且让 207 MB 的包翻倍 |
| 用 OpenCV dnn 跑 Florence-2 | seq2seq + KV cache + 自定义解码，**OpenCV dnn 不支持** |
| 在引擎侧为本地模型**维护跨帧状态** | 已撤销三次（`ai_locate_track`/`ai_locate_cache`/`ai_ui_layout`），理由见 §7 红线 3 |
| 先做"自研微调"再做"接现成模型" | **顺序错了**：先用现成 Florence-2 上线拿真实数据，**数据才让微调有意义** |

| Qwen3-0.6B 社区 **Q4_K_M**（**推算**，非官方仓） | 596M × 4.5bit/8 + 开销 | **≈ 400 MB** |
| SmolLM2-360M-Instruct Q4（**推算**，备选） | — | ≈ 250 MB |
| ONNX Runtime DLL | — | 15~20 MB |
| llama.cpp DLL（若文本侧走 GGUF） | — | 2~5 MB |
| tokenizer / config / LICENSE 等 | — | ~10 MB |

⇒ **三档落地组合**：

| 方案 | 含什么 | 能干什么 | **新增磁盘** | 装后完全体 | 若打进安装包 |
|---|---|---|---|---|---|
| **A 最小** | Florence-2-base int8 + ORT | (b) 定位 + (c) 的"看图" | **≈ 256 MB** | ≈ 813 MB (+46%) | 208 → **≈ 464 MB** |
| **B 推荐** | Florence-2-base **q4f16** + **Qwen3-0.6B Q4** + ORT | (a)(b)(c) 全部 | **≈ 660 MB** | ≈ 1.22 GB (+118%) | 208 → **≈ 868 MB** |
| **C 单模型** | SmolVLM-500M **q4f16** + ORT | 三个都能碰，但 (b) 定位差 | **≈ 285 MB** | ≈ 842 MB (+51%) | 208 → **≈ 493 MB** |

**★ 结论（回答"要加多少"）**：
- **完全体：+256 MB ~ +660 MB**（相对 556.9 MB ⇒ **+46% ~ +118%**）；
- **安装包：若把模型打进去，208 MB → 464~868 MB（翻 2.2~4.2 倍）**；
- ⇒ **所以强烈建议走"可选下载"**（§8）：**安装包保持 208 MB 不变**，
  只有选择安装的用户付出这 256~660 MB。**这是本方案唯一能接受的体积形态。**

⚠ **必须诚实说的三条**：
1. **"+660 MB" 不是"超小"** —— 它比 `opencv_world4100.dll`（61.7 MB）大 10 倍，
   是 `WebView2Fixed`（376.6 MB）的 1.75 倍。**用户说"不要占太多磁盘"，这个量级需要明确告知并让他自己选。**
2. **方案 B 的 660 MB 里，约 400 MB 花在"脚本生成/文字判断"这个纯文本模型上** ——
   而它的收益（见 §15.2）恰恰是三者里最不确定的。**如果先做 (b)，只要 256 MB。**
3. **WebView2Fixed 占 67.6%** —— 如果目标是"整体减体积"，
   **优化 WebView2 的分发方式比砍模型更有效**（本方案不是减体积方案）。

### 14.3 性能占用（**内存是比磁盘更硬的约束**）

| 项 | 推算值 | 说明 |
|---|---|---|
| **常驻内存（只加载 Florence-2-base int8）** | **≈ 500~700 MB** | 236 MB 权重 + 激活 + 特征图 |
| **常驻内存（+ Qwen3-0.6B Q4）** | **≈ +600~900 MB** | 400 MB 权重 + KV cache |
| **两者同时加载的峰值** | **≈ 1.2~1.5 GB** ⚠ | **这是最需要警惕的数字** |
| 单次定位耗时 | 1~3 s（16 线程 int8）/ 4~12 s（弱机 4 线程） | §4.2，**推算** |
| 单次脚本生成耗时 | Qwen3-0.6B 在 CPU 约 **10~30 tok/s**（推算）⇒ 输出 150 token ≈ **5~15 s** | 一次性任务，可接受 |
| 磁盘 IO（冷启动加载） | 读 236 MB / 400 MB ⇒ **数秒**（SSD）/ 更久（HDD） | 建议 `mmap`（llama.cpp 默认） |
| CPU 占用 | 单次推理**打满可用线程** | ⚠ **必须复用 `SyncImageMatchThreadBudget()`** |

**★ 三条硬约束（照做）**：
1. **按需加载 + 用完卸载**，**不要常驻**。两个模型同时驻留 1.2~1.5 GB 会让 8 GB 机器很难受。
   建议：定位模型**懒加载 + 空闲 N 分钟卸载**；文本模型**每次用完即卸**（它只服务一次性任务）。
2. **低性能模式硬禁用**（既有前科，§7 红线 4）。
3. **设置页必须显示实际内存占用与磁盘占用**，让用户在装之前就知道代价。

## 15. 用户新增的三类任务：逐条可行性（这是本轮的重点）

> 用户明确：目标**不只是"给联网 API 加速"**，而是**服务"完全不接 API 的用户"**。
> 三类任务：**(a)** 脚本助手生成简单脚本；**(b)** AI 动作执行时按描述定位点击；**(c)** 图片分析 → 输出变量。

### 15.1 ★ 先看能力矩阵：**没有单个小模型能同时干好这三件事**

| 任务 | 需要的能力 | **Florence-2-base** | **Qwen3-0.6B** | **SmolVLM-500M** |
|---|---|---|---|---|
| **(a) 生成简单脚本** | 文本 → 结构化 JSON 工具调用 | ❌ **不能**（seq2seq，非对话/工具模型，词表是 BART 的，不适合 JSON） | ✅ **本职**（官方 chat template **原生带 `<tools>` / `<tool_call>` 格式**） | ⚠ 弱（可出 JSON 但不稳） |
| **(b) 按描述定位点击** | 图 + 文 → 坐标（grounding） | ✅ **本职**（微调后 ScreenSpot 74.1） | ❌ 无视觉 | ❌ 差（未针对 GUI grounding 训练） |
| **(c) 图片分析 → 变量** | 图 + 文 → 短答案 | ⚠ **一半**（能 caption/OD，但"判断"不是它的强项） | ❌ 无视觉 | ✅ **本职**（VQA/caption 是它的设计目标） |

⇒ **结论：要覆盖 (a)(b)(c)，最少需要两个模型**（Florence-2-base + 一个文本模型）。
**方案 C（SmolVLM-500M 单模型）能"一个顶三个"，但每一项都打折**，尤其 (b) 定位会明显差 ——
**若 (b) 是重点，方案 C 不成立。**

> **★ 顺带一个重要发现**：`Qwen/Qwen3-0.6B-GGUF` 的官方 chat template 里**已经内建了
> `<tools>` / `<tool_call>` 的完整工具调用格式**（本轮从 HF API 直接读到）。
> ⇒ 用它做 (a) **不是"硬凑"，是模型被训练过的能力**。这比随便挑一个 0.5B 通用模型靠谱得多。

### 15.2 (a) 脚本助手生成简单脚本 —— ⚠ **可行，但必须大幅收窄，且这是三者里最不确定的**

**能做**（用户举的例子：鼠标移动、点击、带循环）—— 这类**输出空间极小**的任务，0.6B 是有机会的。

**但必须同时满足四个条件，否则一定失败**：

| # | 条件 | 为什么必须 | 做法 |
|---|---|---|---|
| 1 | **工具集必须收窄到 ≤8 个** | 本仓现有 `src/agent_tools.cpp` **12 万字节源码**，工具数量远超 0.6B 的容量；给全量工具表 ⇒ 必然幻觉字段 | 只暴露 `mouseMove` / `mouseClick` / `keyClick` / `wait` / `loop` 等最小集 |
| 2 | **语法约束解码（GBNF / JSON Schema）** | 0.6B 自由生成 JSON 会漏引号、多逗号、编造字段 | llama.cpp 的 GBNF，或 ORT 侧的受限解码 |
| 3 | **schema 校验 + 修复循环** | 约束解码仍可能语义错（如 `loop` 缺 `count`） | 校验失败 → 把错误回灌 → 重试 ≤2 次 |
| 4 | **不让模型直接写脚本文件** | 复用既有落地链路才有校验 | 模型只出**动作 JSON**，交既有 `buildScriptActions` / `createMacroScript` 落盘 |

**⚠ 三条诚实提醒**：
1. **这条任务的延迟不敏感**（一次性生成，不是每帧）⇒ **云端模型在这件事上天然更好**。
   本地版本的价值**只对"完全离线/完全不接 API"的用户成立**。
2. **成功率必须 A/B 实测**。**0.6B 在窄 schema + 语法约束下"可能"可用，但我不假设它可用** ——
   验收判据必须是「一批真实 prompt 的成功率 + 修不回来的比例」，报区间与样本量。
3. **它需要额外 ~400 MB**（Qwen3-0.6B Q4）—— **性价比是三者里最低的**（见 §14.2 的诚实说明 2）。

### 15.3 (b) 按描述定位点击 —— ✅ **三者里最可行、最该先做**

- **这就是 §1~§12 的方案**：Florence-2-base 微调后 ScreenSpot **74.1**（GoClick 证明 0.23B 可达），
  接入 `FuseLocateCandidates` 作为**同级候选**，复用全套校验闸。
- **预期**：首轮命中 **60~75%**，经校验闸后**错点率 <2%**（§3.3）。
- **只需 256 MB**（方案 A）。
- ⇒ **建议 P1 只做这一条。** 它价值最高、体积最小、技术风险最低、且**顺带为 (a)(c) 积累数据**。

### 15.4 (c) 图片分析 → 输出变量（"有广告→1，否则→0"）—— ⚠ **可行，但有三个必须处理的问题**

**做法（两步流水线）**：
```
截图 → Florence-2-base <MORE_DETAILED_CAPTION> / <OD>  →  文字描述
     → Qwen3-0.6B 读描述 + 用户 Prompt  →  {"value": 0|1|"unknown", "confidence": 0.0~1.0}
```

**⚠ 问题 1：精度一般，且"二元判断"的错法最危险**
- 零样本二元判断精度**推算 70~85%**（**未实测**，必须 P0 量）。
- ⚠⚠ **最危险的失败形态**：模型瞎猜给出一个 `1`，脚本**按确定值走** ⇒
  **静默地把整条流程带错**，用户事后才发现。这正是本项目反复打过的那类 bug
  （「静默点到错的地方」的同构形态）。
- ⇒ **必须三态输出**：`1` / `0` / **`不确定`**，且**脚本层必须处理"不确定"分支**。
  低置信 ⇒ 输出"不确定"，**绝不用默认值兜底**。

**⚠ 问题 2：这个场景本品已有更便宜更准的做法，别用模型硬做**
| 需求 | 更便宜的做法 | 成本 |
|---|---|---|
| 「界面有没有广告」 | **找图（存一张广告模板）** | **毫秒级，接近 100% 准** |
| 「界面上这个数字是多少」 | **OCR** | 几十 ms，更准 |
| 「这个按钮叫什么」 | **UIA 控件树 / OCR** | 零成本 |

⇒ **产品设计建议**：
- **固定判断**（用户能给出样例图的）⇒ **引导他用找图**，不要用模型；
- **任意描述判断**（模型训练时没见过的新判断，且用户给不出模板）⇒ 才用 (c) 这条流水线；
- **UI 上必须标明"本地判断可能有误"**，并给出置信度。

**⚠ 问题 3：需要第二个模型 ⇒ 体积从 256 MB 跳到 660 MB**
- 若用户能接受"只做 (b)"，**先不要引文本模型**（§14.2 方案 A vs B）。

### 15.5 分期建议（按"价值 / 体积 / 风险"排序，**与用户预期的顺序不同**）

| 优先级 | 内容 | 新增体积 | 理由 |
|---|---|---|---|
| **P1** | **(b) 按描述定位点击** | **256 MB** | 价值最高、体积最小、技术最成熟（有 GoClick 论文背书） |
| **P2** | **(c) 图片分析 → 三态变量** | +~400 MB | 可行但精度一般；**必须先解决三态输出与脚本分支**，且要与找图/OCR 分工 |
| **P3** | **(a) 脚本生成** | 复用 P2 的文本模型 | 延迟不敏感 ⇒ 云端天然更好；本地只服务纯离线用户；**必须窄工具集 + 语法约束 + 实测成功率** |

> ★ **注意这里和用户直觉的差异**：用户把 (a) 排在第一位提。
> 但从工程上看，**(a) 是三者里最不确定、性价比最低的**（需要额外 400 MB，而云端在"一次性生成"
> 这个场景上本来就更好）；**(b) 才是那个"只有本地能做、且必须本地做"的事**
> （每帧/每次点击都要定位，云端 10.8 s 根本不可用）。
> **建议先做 (b)，用它的数据与用户反馈决定要不要往 (a)(c) 走。**

## 16. ⚠ 修正记录：§4.2 初稿的"约 0.5 秒"过于乐观

| 项 | 初稿（2026-09-23 早） | 修正后 | 错在哪 |
|---|---|---|---|
| Florence-2-base 单次耗时 | **~0.5 s** | **~1~3 s**（好机）/ 4~12 s（弱机） | **漏算了 BART 编码器要把 ~576 个图像 token 整个编码一遍**（≈170 GFLOPs），只算了 ViT |
| Florence-2-base FLOPs | ~30~50 GFLOPs | **~0.3 TFLOPs** | 同上 |
| Qwen2-VL-2B @1344 FLOPs | ~11 TFLOPs | **~19 TFLOPs** | 漏算了 ViT 部分（~12.4 TFLOPs，1344² 有 9216 个 patch） |
| 相对云端的加速比 | "快约 20 倍" | **快约 3~10 倍** | 由上面两条推出 |

**方向性结论不变**（encoder-decoder 仍比 decoder-only 便宜一个数量级以上），
**但绝对数字变了 2~6 倍** ⇒ §0 的表格已同步修正。

**教训（写下来，别重犯）**：**折算 FLOPs 时不能只看"参数量 × token 数"** ——
encoder-decoder 的图像特征是以 **token 形式进 BART 编码器**的，
它**不参与自回归生成**，但**要整个编码一遍**，这部分很容易被漏掉。
**这也是"推算必须被实测替换"的又一例证**（§12 P0）。
