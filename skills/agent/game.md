# Skill: 实时游戏 / 动态画面（section=game）

> 用途：游戏（尤其**实时类**）、播放器、滚动列表这类**画面一直在动**的场景。
> 归属：产品 Skill（`skills/agent/game.md` → 打包后 `AppDir()\skills\agent\game.md`）。
> ★改本文件必须同步 `src/ai_action_router.cpp` 的内嵌文本 `MacroActionGameSkill()`。
> 结论来源：`docs/realtime-game-vision-loop-research.md`（含各条实测数据与出处）。

## 0. 最重要的一条：**别把 VLM 放在每个动作的路径上**

已发表的「VLM 循环打游戏」方案，没有一个能在不暂停/不减速游戏的条件下实时运行
（Cradle 打 RDR2 要暂停游戏等 GPT-4o；GamingAgent 打俄罗斯方块把事件间隔改成 500~600ms）。
grounding 一次 0.7~6.9 秒，而实时游戏的控制回路是 ~15Hz。所以正确姿势是：

```
① 用 VLM 找一次（贵、准） → ② 之后每帧用**本地**手段跟住（便宜、快）
   → ③ 只在本地判失败时才再叫一次 VLM
```

本地手段按优先级：

1. **颜色**（HUD 血条/蓝条/技能亮灭/小地图点位）：`findColor` / `getColor` / `colorMatch`。
   游戏里颜色比形状稳得多，而且毫秒级、可反复调用。**能用颜色判的就别用识图。**
2. **找图**（图标、按钮、固定 HUD）：`findImage`（宿主已做多尺度 + 唯一性 + 像素终审）。
   - 模板必须**有纹理**：纯色块的归一化相关会「处处满分」→ 宿主的找图引擎会直接拒绝
     这种模板并告诉你原因，遇到这种报错就换 `findColor` 或换一块有纹理的区域。
   - 循环里反复点同一个目标：宿主有定位缓存（命中会打印「定位缓存命中…迟滞 N/3 帧一致」），
     它现在要求**多帧一致**才认，画面抖动时宁可回一次识图，也不会点在残影上。
3. **UIA**：只在普通桌面窗口有用；游戏画面（DirectX/自绘）枚举不到，别浪费时间。

## 0.5 **先搞懂机制再动手**（抽象目标的必经一步）

目标抽象（「帮我通关这关」「打过这一波」「把这个模式通了」）时，**先花一轮把机制搞清楚**，
再开始操作。否则你会按「通用直觉」打，而每种游戏都有反直觉的规则。要搞清楚的是：

1. **胜负条件**：吃光/撑过 N 波/到达某处/分数达标？（画面上的计数器、进度条、波次提示）
2. **资源规则**：这类资源（阳光/费用/能量/冷却）是**全局共享**还是**每种单位各自一份**？
   —— 这是最容易搞错的一条，见下面的实例。
3. **操作机制**：是「先选再点目标」还是「拖拽」？一次能放几个？有没有前置步骤（选卡/布阵）？
4. **节奏**：单位多久出一波？失败是立刻重开还是原地复活？

怎么搞：`lookupMacroAction(section=game)`（本 Skill）+ 看当前画面 + 需要时
`fetchWebPage` 搜「<游戏名> <模式> 玩法/攻略」，然后把**一句可执行的结论**写进
`updateTaskMemo`（例：「僵尸卡各自独立冷却，阳光共享，目标是让僵尸走到最左吃到脑子」）。
操作已经很明确（点这个按钮、按这个键）时**不要**去查——那是浪费 token。

### 实例（真实踩坑，2026-09-17）

《植物大战僵尸融合版》「我是僵尸」模式：AI 以为「冷却一次只能放一个僵尸」，于是
**一次只放一个僵尸去送死**（葫芦娃救爷爷）。实际规则是：**冷却按卡牌各自计算**，
不同卡可以连续放；阳光是共享预算。正确打法是「一次选够卡 → 同时/连续放多个僵尸形成波次」，
而不是一个一个送。这条经验推广开：**凡是「选单位放到场上」的游戏，
先确认冷却/费用是全局的还是每单位独立的，再决定要不要批量放。**

## 0.6 **资源分配先算账**（选卡 / 放单位，别心算）

「给定预算 + 槽位 + 一批候选，怎么花最划算」是有确定解的组合问题，**不要靠模型心算** ——
实测两种典型翻车：① 选卡点「一键全选」，弱卡把卡槽占满、强卡进不来（阳光明明够）；
② 阳光够放几十只，却只放 2~3 只就停手。

用 `planSpend` 算，再照名单执行：

```
选卡：planSpend(budget=总阳光, slots=卡槽数, distinctOnly=true,
               items=[{name:"巨人僵尸",cost:600,value:600}, {name:"路障僵尸",cost:75,value:75}, …])
      → 按性价比给名单；**照着名单逐个点卡，不要一键全选**
放单位：planSpend(budget=当前阳光, distinctOnly=false,
                 items=[{name:"巨人僵尸",cost:600,maxCount:不限}, …])
      → 告诉你这一波放哪些、各放几个；**算出 5 个就一次放 5 个**
```

- `value` 缺省按 `cost` 当强度（贵的通常更强）；能判断强弱就给 value。
- 结果里的「剩多少」用来决定是否再来一波。
- 通用：不只 PvZ —— 商店购物、塔防放塔、卡牌对局、RTS 造兵都是同一套。

## 1. 定位（locateAndClick）在游戏里的正确用法

### 1.0 ★位置只找一次：布局记忆 + 相对网格（省识图的大头）

固定界面（草坪格子、卡槽、桌面图标阵列、工具栏按钮）**不该反复识图**：

- **布局记忆**：同一个窗口（标题/类名/客户区尺寸一致）+ 同样分辨率下，一个目标
  **定位成功一次就记住坐标**，之后再点它直接走记忆（0 次识图，日志会打「布局记忆命中」）。
  换窗口 / 挪窗口 / 改分辨率 / 点下去画面没变化 → 记忆自动作废（不会拿旧坐标乱点）。
- **相对网格**：规则排列的东西定位到**一格**就够 —— `locateAndClick(grid={anchor:"草坪",cells:[[1,3],[2,3]]})`。
  宿主会取一帧画面、用「自位移平均绝对差」找出该方向的**周期**（列距/行距），
  于是整片格子坐标都能算出来；锚点只识图一次，之后每格纯坐标计算。
  `cells` 是相对锚点的 `(行,列)` 偏移：`[0,0]`=锚点本身、`[0,1]`=右边一格、`[1,0]`=下面一行，可为负。
- 看不规则界面（没有明显周期）时宿主会明确拒绝并让你回到逐个描述 —— 那就老实逐个来。

**放置类游戏的标准打法（两次找图覆盖整局放置）**：

```
① locateAndClick(grid={anchor:"草坪", cells:[[0,0]]})   ← 定位草坪锚点（唯一一次识图）+ 建立网格
② locateAndClick(target="僵尸卡")                        ← 定位卡槽（每个卡槽各自一次）
③ 之后每次放置：locateAndClick(grid={anchor:"草坪", cells:[[行,列],…]})
   —— 想同时放多个就一次列多格（≤24），全程 0 次识图
```

### 1.05 一次性按钮 vs 可复用位置（别给「只点一次」的东西上复用那套）

**不是每个位置都值得「记住 / 建网格」**。判断标准只有一个：**这个位置后面还会不会再点？**

| 类型 | 例子 | 怎么做 |
|---|---|---|
| **一次性**（点完这次就不再点它） | 「自选僵尸卡牌」「正常模式」「主菜单」「暂停」「确定/关闭」 | **直接点**：目标的文字就是屏幕上的标签，`locateAndClick(target="自选僵尸卡牌")`，宿主会用本地 OCR 文字索引命中坐标（0 次识图）。**不要**给它建网格、不要指望记忆、更不要为它反复识图确认 |
| **可复用**（同一局里反复点） | 草坪格子、卡槽、道具栏、翻页箭头 | 走 §1.0 的布局记忆 + 相对网格，只为这些付一次识图 |

宿主侧已经把这条做成默认行为：**同一个目标本次运行第一次被点时不会写复用缓存/布局记忆，
第二次才写**（`一次性目标…不写定位模板缓存` 日志）。所以：

- 一次性按钮放心用文字直点，日志出现「文字直点：本地 OCR 索引命中」就是最省的那条路；
- 但**别对同一个一次性按钮连点**（第二次开始才会进复用缓存，意义也不大）；
- 需要反复点的那一个（草坪锚点/卡槽）要**早点定位并让它复用**：第一次
  `locateAndClick(grid={anchor:…})` 之后，后续都用 `grid` 走坐标计算。

### 1.1 通用规则

- **两步操作一次做完**：`locateAndClick(targets=["僵尸卡", "第3行草坪"])`
  —— 一次工具调用里逐个识图定位并**立即连续点击**，中间不插观察/验收。
  这比「先点卡 → 等模型确认 → 再点草坪」省掉一整轮主模型（通常 10~40s 思考）
  和每次 1.5~2.6s 的界面稳定等待。游戏界面在动，**没有逐步确认的价值**。
- **批量进攻**：把「要放的每一处」一次列进 `targets`（最多 6 个），或用连续多条
  `locateAndClick(targets=[...])`；开局选卡同理，一次选够再进游戏。
- **target 要短**（2~10 字）且写屏幕上**真实存在的东西**：「开始挑战」「X 关闭」「确定」；
  别写「画面中间偏右那个红色的按钮」这种长句（VLM 会被带偏）。
- 坐标由宿主换算，**不要自己算像素**；小/糊目标传 `refineLevels=2`。
- 一次定位成功后：**同一个目标**不要再重复识图（缓存会接管）；**换了目标**才需要新定位。
- 找不到就换一句更短的描述或滚动一次；**不要**对同一坐标连点（宿主会拦并警告）。

## 2. 输入手法（游戏专用，别用桌面软件的套路）

| 要做的事 | 用什么 | 注意 |
|---|---|---|
| 按住前进/技能（持续按住） | `keyDown` … `keyUp` | **不要**用 `keyClick` 反复点：游戏读的是按下状态 |
| 转视角/相机（相对移动） | `moveMouseRelative` | 相对位移会被系统**指针加速**缩放（同一份代码在不同机器上落点差 400~1600px）；需要精确时改用「找图/颜色定位 + 绝对移动」，或让用户在系统里关闭「提高指针精确度」 |
| 精确点到 HUD 元素 | `findImage`/`findColor` 拿到屏幕坐标 → `mouseClick` | 绝对定位不受指针加速影响 |
| 技能连招 | `hotkeyShortcut` 或 `keyDown`/`keyUp` 组合 | 应用专属组合键默认被拦，需要 `confirmShortcut=true` |
| 节奏（连点/循环） | 动作的 `duration`（=**重复间隔**）+ `clickCount` | 它**不是**「执行前等待」；宿主按它安排重复节奏 |

- **不要靠 `wait` 凑帧**：`Sleep` 的精度在 Windows 上被量化到 ~15ms 级别，
  固定 `wait 0.016` 得不到 60Hz。要节奏就用动作自带的重复间隔（宿主内部用高精度定时器）。
- 前台独占全屏游戏：合成采集（WGC）与 `SendInput` 都要求窗口在前台；窗口化无边框最稳
  （实测：DXGI 桌面复制在双显卡（Optimus）笔记本上会**必然失败**，宿主的采集链已按
  WGC → BitBlt 兜底，不要自己去找 DXGI 路径）。
- 反作弊：宿主注入的是**标准 SendInput**，会被识别为注入（`LLMHF_INJECTED`），且没有任何
  办法清除该标记。**不要**在带反作弊的在线游戏里跑自动化，先 completeTask 说明风险。

## 3. 动态画面的三段式套路（推荐模板）

```
1) 观察一帧，确定「状态判据」（血条颜色？按钮亮灭？分数数字？）
   —— 优先选颜色/找图这类本地可判的东西，别选「看画面猜」
2) 用 findColor/findImage 判状态 → 满足就用 keyDown/mouseClick 做动作
3) 每轮只做**一个**决策，动作后不要立刻再截图问模型：
   宿主已经做过 settle；连点/长按交给 duration 与 keyDown/keyUp
```

- 「目标在动」时：先用找图/颜色把目标**锁住**（同一轮内完成判状态+动作），
  不要「截图问模型 → 模型回答 → 再截图确认 → 才点」，那中间目标已经走了。
- 需要连续多步（走位/连招）时：可以用 `submitMacroActions` 一次提交一串动作
  （宿主会顺序执行、不逐步识图），这等价于研究里的「speculative multi-action」，
  能把 API 轮次砍掉一大半；但**每一步都要是确定的**（时间/按键/坐标已知），
  不能把「还没定位的东西」写进去。
- 画面大面积在动（视频/游戏）时宿主会主动跳过截图上传省 token，并禁止在动态区域识图；
  这时应该改用颜色/找图/按键，而不是抱怨「看不到画面」。

## 4. 常见错误（会被宿主拦，别踩）

1. 同一坐标连点（宿主有近点重复点击守卫）——想「多点几次」请用 `clickCount` + `duration`。
2. 对动态画面反复 `locateAndClick` 同一个目标（第 4 次起宿主会要求换路线）。
3. 用 `mouseClick` 猜绝对坐标点游戏画面里没定位过的东西（会被拦；先 findImage/findColor/定位）。
4. 用 `wait` 拼节奏、用 `keyClick` 实现长按、用 `quickInput` 往游戏里打字（除聊天框）。
5. 在独占全屏且被其它窗口遮挡时操作（输入打不到前台窗；先 `activateWindow`）。
